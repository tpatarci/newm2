<objective>
Make D-06 literally true: nothing waits for a restart.

Purpose: 09-04 proved live apply against one setting and built the funnel. This plan takes the funnel
to the rest of the surface the GUI edits — nine colours, two fonts, four focus-policy booleans, three
delays, two command settings and the manual menu entries — and adds the reload notice D-08 requires so
an open GUI is never quietly showing a stale picture. CONTEXT.md is explicit that "where possible" in
CGUI-04 is to be read as "always", and equally explicit that if any one setting's live path proves
unsafe it may fall back to next-start **with the record saying which and why**. This plan is where
that judgment gets made, per setting, with evidence.

Output: the remaining branches of `WindowManager::applyConfig()`, a live tab-font reload path in
`Border`, the reload broadcast, the cases that prove each, and a release notes section that no longer
names any restart-only setting.
</objective>

  <behavior>
    - Setting `tab-background` over the socket makes the dominant pixel value of an already-framed
      window's tab rectangle the new colour, at or above the same share threshold the menu paint
      criterion uses.
    - The same holds for `frame-background`, `button-background` and `borders` against their own
      rectangles, and for `menu-background`, `menu-foreground` and `menu-highlight` against a root menu
      opened after the change.
    - `tab-foreground` changes the label ink, asserted as the label pixel no longer being present in
      its old value inside the tab rectangle.
    - The bevel on the focused window's tab is re-derived from the new tab background, not left at
      shades derived from the old one.
    - A colour string the X server cannot parse is refused with an error naming the key, and every
      window keeps the colour it had.
    - Setting the same colour twice performs no second reallocation.
  </behavior>
  <action>
    Extend `WindowManager::applyConfig()` with the colour branch. For each of the nine colour keys
    that differs from the effective config: allocate the new value first, and only on success release
    the old one and store the new. Allocating first is the whole of this task's safety property — a
    failed allocation must leave the window manager with a valid colour, which it cannot do if the old
    one was already freed. On failure, reply with an error naming the key and leave everything as it
    was.

    Colours reach the screen through several holders: the pixel values used for window backgrounds and
    graphics contexts, and the Xft colours the menu and the tab label are drawn with. Update each
    holder, then force the screen to agree: set the new background on each affected window and clear
    it so the server repaints, and re-run the existing paint path for tabs and for the menu rather
    than inventing a second drawing path. Re-derive the bevel shades from the new tab background using
    the existing derivation, so a dark palette gets bevels that belong to it — the release notes
    already promise exactly that.

    Add the cases to `tests/test_wm_config_live.cpp` using the histogram capture idiom already in the
    suite: map a client, capture its tab rectangle, `wm2-ctl set` a colour that is far from the
    default in every channel, capture again, and assert the dominant value changed to the expected one
    with a share at or above the existing named threshold. A colour close to the default would make the
    assertion pass on a repaint that never happened.

    Add the refusal case and the no-op-on-repeat case. For the repeat case, assert on the window
    manager's own behaviour rather than on the screen: a counter or a stderr line is not available, so
    assert instead that the second `set` completes and the captured histogram is byte-identical to the
    first capture — identical output after a second application is what "no second reallocation" looks
    like from outside.
  </action>

    - Setting `tab-font` over the socket while a window is open changes that window's tab width, and
      the label is redrawn in the new face.
    - The change reaches every managed window, not only the focused one.
    - A `tab-font` value fontconfig cannot resolve is refused with an error naming the key; the
      previous face stays loaded and every tab keeps its width.
    - Setting `menu-font` changes the row height of the next root menu opened.
    - Setting `click-to-focus`, `raise-on-focus`, `auto-raise` or `focus-stealing-prevention` changes

    - Setting `auto-raise-delay`, `pointer-stopped-delay` or `destroy-window-delay` changes the

    - Setting `new-window-command` or `exec-using-shell` changes what the root menu's New entry runs.

  <action>
    Give `Border` a reload entry point that loads a new face **before** closing the old one, walks the
    ladder exactly as `loadTabFont()` does, and on total failure keeps the old face and reports
    failure to the caller rather than leaving the shared member null. Then re-measure and re-lay out
    every managed client's tab: the tab width is derived from the face's ascent and descent, so the
    frame, the tab window and the shape must all be recomputed with the same code path that computes
    them at map time — not a second, parallel computation, which is how the two drift.

    Do the same for the menu font in `WindowManager`: load first, swap on success, keep the old on
    failure. The menu is rebuilt per opening, so no re-layout of an existing menu is required; state
    that in a comment so a later reader does not add one.

    For the focus booleans, the three delays and the two command settings, `applyConfig()` only has to
    store them, because each is read at the point of use. Add a case per setting proving that is
    actually true rather than assumed — this is precisely the class of claim 08-07 found to be false
    for these same three booleans, where the values parsed and nothing read them.

    Remove the "takes effect at next start" sentence 09-01 added to `docs/RELEASE-NOTES.md`, since it
    is no longer true.

    **If any single setting's live path proves unsafe** — for example if re-laying out every tab under
    a held grab produces a visible defect — CONTEXT.md D-06 permits that one setting to fall back to
    next-start. In that case: keep the fallback for that setting only, name it and the reason in
    `docs/RELEASE-NOTES.md`, and record it as a decision in the SUMMARY. Do not silently narrow the
    scope; a setting that is not live and not named is the failure this instruction exists to prevent.
  </action>

  <name>Task 3: the root menu rebuilds, and every connected client learns the file changed</name>
  <files>src/Manager.cpp, src/Buttons.cpp, tests/test_wm_config_live.cpp</files>
  <read_first>
    - `src/Buttons.cpp` — `WindowManager::menu()`'s entry assembly: the create label, the hidden
      clients, the categories, and the exit slot
    - `src/Manager.cpp` — where manual menu entries are merged into the category list at startup, and
      `include/AppCache.h` for the category source
    - `src/Config.cpp` — the `menu-entry-name` / `-command` / `-category` accumulator, which is the
      grammar a `set` of a menu entry has to speak
    - `include/SocketServer.h` — `broadcast()` from 09-03
    - `09-CONTEXT.md` D-08 and D-12
  </read_first>
  <behavior>
    - After the manual menu entries change, the next root menu opened shows the new entry list; a
      menu already open is not disturbed.
    - Removing every manual entry removes their category from the menu when nothing else populates it.
    - When the window manager re-reads its config layers from disk, every connected socket client
      receives a reload notice on its own connection.
    - A client that connected but never sent a hello receives no broadcast, because it is not a
      client yet.
    - The broadcast carries no payload beyond its type; a client that receives it re-asks for what it
      needs. This keeps the notice from becoming a second, drifting copy of the settings.
  </behavior>
  <action>
    Decide and record how a manual menu entry set is carried over a protocol whose values are flat
    strings. The three-key accumulator grammar the config file uses is ordered and stateful, which a
    single request-reply message is not. Use the grammar the file already defines, applied through the
    same parser: a menu-entry `set` carries the whole entry list in the file's own key order as one
    value, replacing the list wholesale rather than mutating it in place. Wholesale replacement is
    what makes the operation idempotent and what makes the GUI's Add/Edit/Remove rows (D-12) map onto
    it without a per-row protocol. Record this in `include/ConfigProtocol.h`'s comment block so the
    GUI and `wm2-ctl` agree.

    Extend `applyConfig()` to rebuild the category list when the manual entries differ, using the same
    merge the startup path uses — not a second merge. Guard against rebuilding while a menu is open:
    if a menu is currently mapped, apply the new list and let the next opening pick it up, rather than
    mutating the list a live modal loop is iterating.

    Add the reload broadcast: after a disk reload completes, encode one notice and hand it to the
    socket server's broadcast, which writes it to every connection that has completed a hello.

    Add the cases to `tests/test_wm_config_live.cpp`: a menu entry added over the socket appearing in
    the next menu; entries removed; a menu open across a change not being disturbed; a connected
    client receiving the notice after a reload; a hello-less connection not receiving it.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| socket value -> X resource allocation | Colour strings and font patterns from a connected process reach the X server and fontconfig. |
| socket value -> the root menu's entry list | A menu entry's command becomes something the window manager will later execute. |
| window manager -> every connected client | The broadcast writes to descriptors the window manager does not own the far end of. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-9-26 | Denial of Service | a colour or font that fails to resolve after the old one was released | high | mitigate | Allocate-then-swap in both paths: the old value is released only after the new one succeeds. Asserted by refusal cases that check the screen is unchanged and the window manager still frames, and by the ASan tree. Standing prohibition in this plan. |
| T-9-27 | Denial of Service | repeated font reloads leaking Xft faces | high | mitigate | Every swap closes exactly one face and the diff prevents a no-change reload from doing any work. The ASan tree with the existing font-resource cases is the gate; `bash scripts/gates/build-all.sh asan` must be green. |
| T-9-28 | Tampering | a menu entry set over the socket introducing a command the user did not type | medium | mitigate | The entry list goes through `Config::applyKeyValue()`'s existing accumulator, which tokenises manual entries by whitespace and does **not** shell-evaluate them; the existing `exec-using-shell` guarantee (threat T-8-SHELL, asserted by a filesystem witness) is unchanged. The socket is reachable only by the user's own uid (T-9-11), so this adds no reachability the user did not already have. |
| T-9-29 | Elevation of Privilege | setting `exec-using-shell` over the socket to make the New entry shell-evaluate | medium | mitigate | Same reachability argument as T-9-28 — only the user's own uid can send it, and that user can already edit the config file. The setting stays documented as shell-evaluated, and the existing both-settings test coverage stays green. |
| T-9-30 | Denial of Service | a broadcast blocking on a client that is not reading | high | mitigate | Broadcast writes are non-blocking to descriptors already marked non-blocking; a write that cannot complete drops that connection rather than waiting. A case connects a client that never reads and asserts the window manager stays responsive. |
| T-9-31 | Information Disclosure | the reload notice carrying configuration values to a client | low | mitigate | The notice carries its type and nothing else; the client re-asks. Asserted by a case reading the broadcast line and checking its field set. |
| T-9-32 | Denial of Service | mutating the category list while a modal menu loop iterates it | high | mitigate | The rebuild is deferred when a menu is mapped; a case holds a menu open across a change and asserts responsiveness. This is the same class of defect the menu rebuild in 08-13/08-14 already fixed once. |
</threat_model>
