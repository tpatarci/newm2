<objective>
Turn the socket from something that answers questions into something that changes the desktop, and
ship the dependency-free command-line client that is both a user-facing tool and the reference client
the test suite drives the protocol with.

Purpose: D-17 puts `wm2-ctl` in the window manager package precisely so a droplet with no desktop
open can be driven over SSH, and so the protocol has a client that is not the GUI. D-06 says nothing
waits for a restart. This plan proves both against the hardest single setting — frame thickness,
which changes the geometry of every frame, tab and resize handle already on screen — and leaves the
remaining settings to 09-05.

Output: `apps/wm2-ctl/main.cpp` and its CMake target, the `get`/`set`/`reload` half of the
dispatcher, `WindowManager::applyConfig()` as the single funnel for live change, frame thickness
applied live, and a fixture-driven test binary that uses `wm2-ctl` as its client.
</objective>

<decisions_recorded>
Claude's Discretion items decided here:

- **DISC-06a — the live-apply funnel.** `void WindowManager::applyConfig(const Config& next)` is the
  only way a configuration change reaches running state. It diffs `next` against `m_config` field by
  field and re-applies only what changed. Every later plan adds branches to this one function rather
  than adding a second application path, so "what is live" has exactly one answer and one place to
  read it.
- **DISC-07 — effective config versus saved file.** The window manager holds two `Config` values:
  `m_config`, the effective one it is drawing with, and a saved-file snapshot taken the last time the
  layers were read from disk. `reload` re-reads the layers, replaces the snapshot, and applies the
  result. `revert` on the GUI side is therefore expressible as "send the saved values back", with no
  new message type.
- **DISC-01a — `wm2-ctl` exit codes.** `0` acknowledged, `1` the window manager replied with an error
  (the reason goes to stderr with the project's `wm2:` prefix), `2` no socket to talk to, `3` usage
  error. A shell script can branch on "not running" separately from "refused", which is the whole
  point of having a CLI.
- **DISC-01b — how `wm2-ctl` finds the socket.** It resolves the same path `configSocketPath()` builds,
  from `$DISPLAY` and the runtime directory, and accepts `--socket <path>` to override. It
  deliberately does **not** read the root-window property, because reading it would mean linking X11
  into a tool whose entire value is that it does not.
</decisions_recorded>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| socket message -> `Config::applyKeyValue()` | A key and a value from a connected process reach the same parser the config file uses. |
| validated config -> `applyConfig()` -> live X11 state | Accepted values become geometry, colours and policy on a running desktop. |
| `wm2-ctl` argv -> the socket | Whatever the user typed is forwarded; the tool does not validate on the window manager's behalf. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-9-20 | Tampering | a `set` carrying an out-of-range or nonsense value | high | mitigate | Every `set` is applied to a **copy** of the config through `Config::applyKeyValue()` — the same function, with the same clamps, the config file goes through — and only a clean acceptance reaches `applyConfig()`. Asserted by refusal cases for both bounds and for an unknown key. Standing prohibition in this plan. |
| T-9-21 | Denial of Service | a frame thickness at the top of its range applied with many windows open | medium | mitigate | The range is already clamped to 1..50 by the existing parser, and the re-layout walks the client list once without reparenting. A `[wm_config_live]` case applies the maximum with several windows mapped and asserts the window manager stays responsive. |
| T-9-22 | Denial of Service | repeated `set` messages causing repeated re-layout | medium | mitigate | `applyConfig()` diffs before it acts, so an unchanged value performs no work at all. Asserted by the idempotency case, which requires byte-identical geometry and no second reconfiguration. |
| T-9-23 | Tampering | `reload` reading a file an attacker replaced | medium | accept | The file is in the user's own configuration directory and the window manager runs as that user; a process that can rewrite it can already do anything the user can. Accepted with the reason recorded, consistent with the existing config-manual-entries disposition. |
| T-9-24 | Elevation of Privilege | `wm2-ctl` being used from a different account | high | mitigate | `wm2-ctl` gets no privilege of its own; the boundary is the window manager's peer-uid check from 09-03 (T-9-11), which refuses the connection before any message is read. |
| T-9-25 | Repudiation | a `set` changing the desktop with no trace | low | accept | The change is immediately visible to the user at the screen, and the file is untouched, so there is no divergence to reconstruct later. Accepted. |
</threat_model>

  explicit acceptance criterion: applying the same `set` twice produces the same acknowledgement, the
  same geometry, and no second re-frame, because `applyConfig()` diffs before it acts. Authored as a

  with an explicit acceptance criterion: messages are applied in arrival order in the event loop's own
  single thread, so no two applications interleave; and a message arriving during a modal grab is
  applied without waiting for the grab, which 09-03's shared descriptor set is what makes true.
  Authored as a `must_haves.truths` entry. Status: **resolved (explicit)**.
