<objective>

Build the two display-free pieces this phase's whole protocol and file story rest on, before anything
opens a socket or a window: the newline-delimited JSON codec, and the surgical config-file writer.

Purpose: both are pure logic with no X11, no GTK and no I/O beyond one file, which is exactly what
the house pattern (`include/MenuPaint.h`, `include/EventPump.h`, `include/TimestampWait.h`) exists to
isolate — logic lifted out of a loop so a Catch2 case can reach it with no display. Getting them
right and exhaustively tested here is what lets plans 09-03 through 09-07 spend their budget on
integration rather than on parsing bugs. It is also the only place in this phase where the wire
contract can still be changed cheaply, which is why the plan opens with a decision checkpoint.

Output: `include/ConfigProtocol.h`, `include/ConfigFileWriter.h`, `src/ConfigFileWriter.cpp`, two new
Catch2 targets with no X11 linkage, and their CMake registration.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <decision>Freeze the version-1 wire contract: the message set, the framing bound, the socket path spelling, and the root-window property name.</decision>
  <context>
    This is the one genuinely one-way door in Phase 9, and CONTEXT.md leaves it to Claude's
    Discretion rather than deciding it — so it has not been walked through yet.

    Everything else in this phase can be revised later. This cannot. `wm2-ctl` ships in the window
    manager package (D-17) and the release notes will document it, so from the moment v1.0 ships, a
    user's shell script, a monitoring cron job or a third-party client may depend on the exact
    message names, the exact socket path and the exact property name. D-8.5-01 established this
    project's rule for that situation: a name is free to change before v1.0 and breaking after, with
    no deprecated aliases. D-16's uid boundary is described in CONTEXT.md as one-way *in spirit* for
    the same reason — the release notes will have promised it, and loosening it later widens a
    security boundary a user was told was closed.

    Undoing this after v1.0 means either a protocol version negotiation with two code paths in three
    binaries, or a documented breaking change. The decision is therefore taken by a human, once,
    before the codec is written — not discovered afterwards.

    All three options implement D-14 (status only), D-15 (hello handshake first, both ways) and D-16
    (same uid only) identically. They differ only in how much surface version 1 commits to.
  </context>
  <options>
    <option id="minimal">
      <name>Minimal set — exactly what D-14/D-15/D-17 name</name>
      <pros>
        Eleven message types and nothing more: `hello`, `hello-ack`, `get`, `value`, `set`, `ack`,
        `error`, `reload`, `reloaded`, `status`, `status-reply`. Every one is required by a locked
        decision, so nothing in version 1 is speculative. Smallest surface to keep working forever.
        Socket path `$XDG_RUNTIME_DIR/wm2-born-again/socket<display>` (fallback
        `/tmp/wm2-born-again-&lt;uid&gt;/socket&lt;display&gt;` per D-16), root property
        `_WM2_CONFIG_SOCKET` holding that path as an `XA_STRING`. Framing: one JSON object per line,
        newline-terminated, 4096-byte bound matching the config parser's own per-line guard.
      </pros>
      <cons>
        Adding a message later (for example the deferred per-window list D-14 explicitly leaves for a
        later phase) means either bumping the protocol version or accepting that older clients see an
        unknown type. The decoder's named `UnknownType` enumerator makes that survivable, but it is
        still a compatibility conversation later.
      </cons>
    </option>
    <option id="minimal-plus-capabilities">
      <name>Minimal set plus a `capabilities` list in the hello acknowledgement</name>
      <pros>
        Same eleven types, but the window manager's `hello-ack` also carries a list of message-type
        names it speaks. A future client can then discover what this window manager supports instead
        of inferring it from a version number, which makes adding message types later additive rather
        than breaking.
      </pros>
      <cons>
        One more field to keep correct forever, and a second source of truth about what the protocol
        speaks (the list and the dispatcher can disagree). Version 1 has exactly one implementation
        on each side, so the discovery mechanism has nothing to discover yet.
      </cons>
    </option>
    <option id="defer">
      <name>Do not freeze — write the codec and revisit the contract before v1.0 ships</name>
      <pros>
        No decision taken under uncertainty; the shape can follow whatever the GUI turns out to need.
      </pros>
      <cons>
        The contract gets frozen anyway, silently, by whichever plan ships first — which is precisely
        the failure mode this checkpoint exists to prevent. It also means `wm2-ctl`, the GUI and the
        window manager may each be written against a slightly different assumed shape.
      </cons>
    </option>
  </options>
  <resume-signal>Reply `minimal`, `minimal-plus-capabilities`, or `defer`. `minimal` is the recommendation: it is the smallest surface that satisfies every locked decision, and the decoder's named `UnknownType` enumerator already gives later versions a non-crashing path.</resume-signal>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| socket bytes -> `configProtocolDecode()` | Untrusted bytes from any process that got past the uid check reach a hand-written parser. This is the phase's primary parsing surface. |
| GUI form state -> `configFileWrite()` | Values a user typed, and values that arrived over the socket, are written into a file the window manager will parse at next start. |
| temporary file -> `rename()` | A file is created beside the user's config and then replaces it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-9-05 | Denial of Service | `configProtocolDecode()` given an oversized line | high | mitigate | The length bound is checked first, before any scan; the decoder never grows a buffer for the caller. A `[config_protocol]` case feeds a line one byte over the bound and asserts the length-specific result. The caller in 09-03 additionally bounds its own read. |
| T-9-06 | Denial of Service | `configProtocolDecode()` given deeply nested or adversarially escaped input | high | mitigate | The grammar is deliberately one level deep with no recursion, so there is no nesting depth to exhaust. A case feeds nested objects and asserts the malformed result rather than a crash or a hang. Built and run in the ASan tree by `build-all.sh`. |
| T-9-07 | Tampering | `configFileWrite()` corrupting the user's config file | high | mitigate | Temporary file in the same directory, fully written and `fsync`-ed, then `rename()`-ed. A case asserts the original survives a simulated failure before the rename. |
| T-9-08 | Tampering | `configFileWrite()` writing outside the file it was handed | high | mitigate | The only paths constructed are the target and a temporary derived from it; a case runs the writer against a temp directory and asserts no file was created anywhere else. The system-wide config file is never a target — a prohibition in this plan's `must_haves`. |
| T-9-09 | Information Disclosure | error text from a failed write echoing a path into a log | low | accept | The path is the user's own config file in their own home directory; the process already runs as that user. Accepted, with the standing rule that no test evidence may carry a host identifier. |
| T-9-10 | Repudiation | a save that partially applied with no record of which half landed | medium | mitigate | The rename makes the outcome binary: either the whole edit set is in the file or none of it is. There is no partial state to record. |
</threat_model>
