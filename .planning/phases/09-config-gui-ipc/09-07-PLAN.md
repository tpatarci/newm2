<objective>
Finish the window: the two remaining pages, and the three moments where the GUI and the file can
disagree — closing with unsaved changes, the file changing underneath, and resetting a whole page.

places CONTEXT.md is explicit that the desktop must never quietly diverge from the file. Those two
decisions are the reason this is its own plan rather than a continuation of 09-06: they are state
machine work, not widget work, and they are where a settings tool usually goes wrong.

  <behavior>
    - Closing the window with no unsaved changes closes it.
    - Closing with unsaved changes presents Save, Discard and Cancel. Save writes and closes; Cancel
      returns to the window unchanged; Discard sends the saved values back to the running window
      manager and then closes, so the desktop matches the file afterwards.
    - Discard in file-only mode closes without sending anything, because there is nothing running to
      return.
    - On receiving the reload notice, the GUI re-reads effective values, keeps every unsaved edit,
      marks each edited control as differing from the file, and shows a one-line notice.
    - A reload notice arriving while a dialog is open does not close the dialog or discard its
      contents.
    - Reset all on a page marks every setting on that page for removal; Save then removes those lines
      from the user file and writes no defaults; Revert before Save undoes the marking.
  </behavior>
  <action>
    Implement the close prompt as a modal dialog with the three responses D-07 names, wired to the
    window's delete event so both the close button and the window manager's own close path go through
    it. Discard's extra step — sending the saved values back — is the whole point of the decision:
    without it, closing the GUI can leave a desktop that does not match any file, which is the state
    a user cannot reason about later.

    Implement the reload notice handler: re-read effective values, then for each key compare the new
    effective value against the form's value and the saved value, and mark the control as differing
    only where the user has an unsaved edit. Show the one-line notice in the same place the banner
    lives so there is one status region rather than two. Do not touch a control the user is currently
    editing beyond the mark — silently replacing text under a cursor is the failure this decision
    exists to prevent, and it is a standing prohibition in this plan.

    Implement Reset all per page as the per-setting reset applied across the page's keys, so there is
    one meaning of reset and one code path.

    Add cases for every behaviour above. Drive the close prompt through the model rather than through
    synthesised input where practical, and note in the SUMMARY which edges the human check below is
    covering instead.

    Build the tree, start a window manager and `wm2-config` on an Xvfb display, and capture

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| user-typed menu command -> the config file -> the window manager's spawn path | A string the user types becomes something the window manager will later execute. |
| the window manager's reload notice -> the GUI's form state | An external event mutates what the user is looking at. |
| GUI close -> the running desktop's state | A destructive-feeling moment where the desktop can be left in a state matching no file. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-9-40 | Tampering | a menu command containing shell metacharacters being silently shell-evaluated | high | mitigate | The command is tokenised exactly as the config parser tokenises it — whitespace only, no shell — and the dialog **shows** the resulting argument vector so the user can see the metacharacter is a literal. The existing shell-evaluation guarantee and its filesystem-witness test are unchanged. |
| T-9-41 | Elevation of Privilege | turning on the shell flag without understanding it | medium | mitigate | The checkbox's label states the shell-evaluation consequence plainly rather than naming the flag. The setting remains off by default, as it already is. |
| T-9-42 | Tampering | a reload notice overwriting an unsaved edit | high | mitigate | The handler re-reads effective values but never replaces a value the user has edited and not saved; it marks the difference instead. A standing prohibition in this plan and asserted by two cases, including one with a dialog open. |
| T-9-43 | Repudiation | closing the GUI leaving the desktop matching no file | high | mitigate | The close prompt forces an explicit choice, and Discard actively returns the window manager to the saved file rather than merely closing. A standing prohibition in this plan, asserted by a case that compares the window manager's state to the file after Discard. |
| T-9-44 | Denial of Service | a very large menu entry list sent as one value exceeding the protocol's line bound | medium | mitigate | The value is bounded by the protocol's 4096-byte line limit; the page refuses to commit a list that would exceed it and says why, rather than sending a message the window manager will reject with an opaque error. A case asserts the refusal message names the limit. |
| T-9-45 | Information Disclosure | screenshots carrying host identity or real user paths | medium | mitigate | Captured on a fixture Xvfb display; the acceptance criteria require each image to be checked before it is committed. Standing rule for a public repository. |
</threat_model>
