<objective>
Open the window. Build the GTK3 application, its connection to the running window manager, and the
first of its three pages — and make the whole thing optional at build time so the window manager is
unaffected by its existence.

Purpose: CGUI-01 asks for a separate GTK3 binary; CGUI-05 asks that the window manager work without
GTK installed. Those two are one design problem, so this plan does both at once: the build option and
the first page ship together, and the proof that the window manager is untouched is a build, not an
argument. This is the project's first GTK surface — `09-PATTERNS.md` finds no analog anywhere in the
tree — so the plan leans on the research's static-callback pattern rather than on a house convention
that does not exist.

Output: a `BUILD_CONFIG_GUI` option defaulting to AUTO, an optional `gtk+-3.0` probe in the preflight
script, the application shell with its three-page notebook and connection banner, a GLib-integrated
protocol client, a display-free form-state model, the Appearance page, and a smoke test that skips
with a stated reason when the GUI was not built.
</objective>

<assumption_delta_decision>
The deterministic assumption-delta scan fired on this phase
(`/tmp/w12/assumption-delta-09.json`): `detected: true`, one signal of kind `optional`, on the
roadmap line *"The WM runs perfectly without GTK3 installed — the config GUI is an optional separate
package."* The `optional` family's question is: **is the old anchor still the right one, or has the
anchor moved?**

**The noun that is now primary: the installable component, not the binary.**

Until this phase, `wm2-born-again` — the window manager executable — *was* the project's install
surface. There are no install rules in `CMakeLists.txt` at all today, so "what gets installed" has
never had to be named. The moment a second, optional artefact exists, the binary can no longer be
that anchor: the question "what does this package depend on?" now has two answers, and only one of
them may mention GTK.

**Decision: `promote`.** The generalized representation — the named install component — becomes
primary, and the window manager binary is demoted to a member of one component (`wm`) rather than
being the install surface itself. This is D-19's two-component split, adopted here as the identity
model rather than as a packaging detail. It is implemented in 09-08.

**Why not `add-alongside`:** keeping the binary as "the install" and bolting the GUI on beside it is
the shape that silently produces a window manager package with a GTK dependency, because there is no
named boundary for the dependency to be excluded from. The generalization would be contradicted by
the still-required old primary — exactly the failure this checkpoint exists to name.

**Companion invariant test (accepted; implemented in 09-08):** *for every build configuration, no file
in the `wm` component's install manifest links GTK or GLib.* That assertion goes red the instant a
future phase reintroduces the singular assumption, so the regression cannot land quietly.
</assumption_delta_decision>

<decisions_recorded>
Claude's Discretion items decided here:

- **DISC-08 — layering beyond D-04.** A key whose effective value comes only from the system-wide layer
  is shown as its effective value, with the raw field's tooltip naming the layer it came from.
  Editing it writes an override into the user file; resetting it removes that override so the system
  value shows through again. The system file is never written.
- **DISC-09 — GTK smoke technique.** The smoke test spawns `wm2-config` under the existing Xvfb fixture
  and asserts at the X level that the application's window is mapped, using the window-tree
  inspection the suite already uses. It deliberately does **not** assert clean stderr (the research's
  Pitfall 3: GTK's accessibility bridge warns on a host with no session bus), does not use the
  accessibility bus, and does not synthesise input.
- **DISC-10 — live preview of a sample tab.** Backlogged, not built. CONTEXT.md offered it as
  "planner may include if cheap"; it is not cheap — drawing a faithful preview means reimplementing
  the rotated-text tab layout outside the window manager, which is a second renderer that can
  disagree with the real one. With live apply working, the real tab on screen **is** the preview.
  Recorded so the omission is a decision rather than a gap.
</decisions_recorded>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| GUI process -> the window manager's socket | The GUI is a client of a boundary the window manager enforces; it holds no privilege of its own. |
| GUI form values -> the user's config file | Values a user typed become a file the window manager parses at next start. |
| GTK and its transitive dependencies -> the GUI process | A toolkit with a large dependency surface, including an accessibility bridge that reaches for a session bus. |
| the build system -> the window manager's link line | The one place a GTK dependency could leak into the window manager. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
