## Summary

Two gaps were recorded in `08.5-VERIFICATION.md`. **One of them is already
closed.** Plan 08.5-03 landed at `195ac51` *after* the verification report was
written, and this research re-measured every one of the five artifact issues that
report lists, plus both of its named replacement guards, against
`docs/RELEASE-NOTES.md` at HEAD. All are clean. Gap 1 needs no plan.

Gap 2 is fully open and is now harder than it was, because plan 08.5-04 tried to
capture the bundle and discovered the gate is not reliably green: **2 of 5 full
debug runs red at 313 tests, a different single case each time.** The operator
held the capture and has now ruled that the flake is to be fixed first.

This research's central contribution is a **named, in-repo, falsifiable
mechanism** that unifies both observed failures, which the 04 measurement
correctly declined to attribute. `WindowManager::loop()` invalidates the
timestamp cache on every event-loop iteration, and the very next
`timestamp(false)` call performs an **unbounded blocking `XMaskEvent`** on the
WM's single-threaded event loop. While it blocks, the WM services no MapRequest
and dispatches no spawn — which is precisely the pair of symptoms observed (#93
"the client was never framed"; #198 "the spawn never happened"), in a different
case each run, one per run. It is queue-ordering-dependent, so it does not
reproduce in isolation, which is why 12 isolated runs of case 198 found nothing.

The research also **rules out**, on read evidence rather than on assumption, the
whole family of hypotheses the brief asked to consider first: ctest `-j`
parallelism, DISPLAY collision between concurrent binaries, `xvfb-run -a` port
races, and `~/.Xauthority` contention. None of them apply to this repository. The
gate runs ctest **serially**, and the fixture reserves each display under an
exclusive `flock`.

**Primary recommendation:** Plan a diagnose-then-fix sequence that lands one
cheap, non-ptrace instrumentation change first (WM stderr trace around the
blocking branch, plus a fix to case 198's `INFO` scope bug that currently
*discards* the WM stderr it captures), re-runs the suite to attribute the failure
from a committed log, then bounds the `XMaskEvent` wait and re-measures the red-run
rate over enough consecutive runs to make "green in one shot" mean something.
Only then capture the four blockers into `evidence/gates/` at the final commit,
following Phase 8's twelve-artifact layout.

## Architectural Responsibility Map

Tiers here are the ones this project actually has: there is no browser, no API and
no database. The meaningful boundaries are process, X server, harness and record.

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Blocking-wait defect in the WM's event loop | **WM process** (`src/Events.cpp`, `src/Manager.cpp`) | — | The unbounded `XMaskEvent` is shipped product code, not test code. A harness workaround would hide a defect a user on a busy VPS can hit. |
| Attribution instrumentation (why did the WM stop?) | **WM process** (stderr) | Test harness (capture) | The WM already writes diagnostics to stderr with the `wm2: ` prefix; `WmFixture` already captures child stderr to a file. Both halves exist — only the trace and the `INFO` scoping are missing. |
| Deadline / spacing policy for synthetic input | **Test harness** (`tests/`) | — | `dragSettle()`'s 90 ms and `selectFirstMenuEntry()`'s zero spacing are test-side timing assumptions. They belong in the harness and must not leak into the product. |
| Display allocation and isolation | **Test harness** (`tests/support/WmFixture.h`) | Host (`/tmp/.X11-unix`) | Already correct: per-fixture `flock` reservation. The *leak* of servers is a host-tier consequence of `setsid()` + ctest TIMEOUT, not a harness design flaw. |
| Suite scheduling / parallelism | **Gate script** (`scripts/gates/build-all.sh`) | CMake test properties | The script owns the single ctest invocation. It is already serial; `RESOURCE_LOCK`/`RUN_SERIAL` in CMakeLists are inert under it. |
| Gate evidence capture and provenance | **Record tier** (`evidence/gates/`) | Gate script | A bundle is a snapshot bound to one commit by `PROVENANCE.txt`. Nothing re-validates it when a later commit lands — that limit is stated, not engineered away. |
| Signoff citations | **Record tier** (`COMPILED_CODE_BEHAVIOR_CHECKLIST.md`) | — | Owned by plan 08.5-05, already written. Not this research's scope. |

**Tier misassignment to watch for in planning:** the tempting fix is to raise
`dragSettle()` from 90 ms to 200 ms, or to bump `kSpawnObserveMs` past 45 s. Both
are **harness-tier patches for a WM-tier defect**. They would green the gate
without fixing anything and would make the next occurrence slower to find. The
plan-checker should reject any task whose only change is a widened test deadline.

## The flake: what the evidence rules out

The brief asked to consider seven mechanisms. **Four of them do not apply to this
repository at all**, and ruling them out cheaply is worth more than investigating
them expensively. Each is refuted by a line of source read this session.

### RULED OUT — ctest `-j` parallelism against a shared server

`scripts/gates/build-all.sh` contains exactly one test-runner invocation, and it
carries no `-j`:

```bash
# The single test-runner invocation in this file. Every future edit must keep
# the --no-tests=error flag attached to it.
run_suite() {
    local tree="$1"
    ctest --test-dir "build/$tree" --output-on-failure --no-tests=error
}
```

[VERIFIED: `scripts/gates/build-all.sh` — `run_suite()`, quoted verbatim above]

ctest's default is one job. **The gate runs 313 tests strictly serially.** Every
hypothesis that requires two test binaries to be running at the same instant is
dead on arrival for this gate.

### RULED OUT — DISPLAY collision between concurrently running test binaries

Two independent reasons. First, serial execution (above). Second, the fixture does
not share a display even in principle:

```cpp
    bool allocateDisplay()
    {
        constexpr int kBase = 120;
        constexpr int kMaxCandidates = 80;

        for (int n = kBase; n < kBase + kMaxCandidates; ++n) {
            if (!m_reservation.tryReserve(n)) continue;
```

and the reservation is an exclusive `flock`, not a scan:

```cpp
        if (::flock(fd, LOCK_EX | LOCK_NB) != 0) {
            ::close(fd);
            return false;   // another fixture in this ctest run owns it
        }

        // Re-check after taking the lock: an external X server may have claimed
        // the display between the scan and the flock.
```

[VERIFIED: `tests/support/WmFixture.h` — `DisplayReservation::tryReserve()` and
`WmFixture::allocateDisplay()`, quoted verbatim above]

The shared-`:99` targets (`test_smoke`, `test_client`, `test_xft_poc`,
`test_ewmh`) additionally carry `RESOURCE_LOCK "x_display_99"` in `CMakeLists.txt`
[VERIFIED: `CMakeLists.txt:199,243,263,280`], which is a no-op under serial
execution but means the design was already correct for `-j`.

### RULED OUT — `xvfb-run` server reuse and `-a` port races

The fixture never invokes `xvfb-run`. It `fork`/`exec`s `Xvfb` directly with an
explicit, already-flocked display number:

```cpp
        std::vector<std::string> argv{
            "Xvfb", m_display, "-screen", "0", "1024x768x24",
            "-ac", "+render", "-noreset", "-nolisten", "tcp"
        };
```

[VERIFIED: `tests/support/WmFixture.h` — `WmFixture::spawnXvfb()`, quoted verbatim]

`xvfb-run -a`'s race is a property of `xvfb-run`'s own display-search loop. There
is no `xvfb-run` in this repository.

### RULED OUT — `~/.Xauthority` contention

The fixture's `Xvfb` argv (quoted above) passes `-ac` (disable access control) and
**no `-auth`**. Nothing in the fixture, the driver or the WM child touches
`~/.Xauthority`. [VERIFIED: `tests/support/WmFixture.h` — `spawnXvfb()` argv
carries `-ac` and no `-auth`; the child environment built in `spawnWm()` sets only
`ASAN_OPTIONS`, `LSAN_OPTIONS`, `UBSAN_OPTIONS` and `DISPLAY`]

The host's *own* long-lived `Xvfb :20` does use `-auth /home/tomislav/.Xauthority`
[VERIFIED: `ps -eo args` output, 2026-08-30], but it is not in the fixture's
`:120`–`:199` pool and no test connects to it.

### RULED OUT — the known intermittent explains it

`[wm_menureopen]` fired **0 of 5 runs**
[VERIFIED: `.planning/phases/08.5-v1.0-closeout/evidence/gates/flake-measurement/README.md`,
"fired in zero of these five runs"]. The 04 halt record is right that deferred
item 12's framing does not cover either observed failure. **This research does
not overturn that — it narrows it.** See the caution under Pitfall 2: ruling out

### NOT RULED OUT — fixture teardown races and leftover servers

This one survives, but as an *aggravator*, not a cause. See "Runtime State
Inventory" below: 19 orphaned `Xvfb` servers are live on this host right now,
occupying `:120` and `:122`–`:134` inside the fixture's own pool, plus a `:121`

skip 15 candidates before it finds a free display.

The leak mechanism is identifiable: both children call `::setsid()` before


should not claim it does. It matters for two other reasons: it is the reason a
clean-slate re-measurement needs a documented pre-run sweep, and it is a real
housekeeping defect worth one line in the fix plan.

## The flake: the leading hypothesis, and why it fits every observation

**Confidence: MEDIUM. The code facts are read and quoted. The causal attribution
is `[ASSUMED]` until one committed log confirms it — which is a single run's
work.** This is stated in exactly these terms because the 04 halt record
established that an attribution is withheld until the measurement supports one,
and that discipline is worth more than a fast answer.

### The mechanism

`WindowManager::loop()` invalidates the timestamp cache on **every** iteration,
immediately after `nextEvent()`:

```cpp
    while (m_looping) {

        nextEvent(&ev);
        m_currentTime = CurrentTime;
```

[VERIFIED: `src/Events.cpp:18-20`, quoted verbatim]

`timestamp(false)` treats `CurrentTime` as "cache is cold" and takes an
**unbounded blocking wait** on the WM's only thread:

```cpp
Time WindowManager::timestamp(bool reset)
{
    if (reset) m_currentTime = CurrentTime;

    if (m_currentTime == CurrentTime) {
        XEvent event;
        XChangeProperty(display(), m_root, Atoms::wm2_running,
                        Atoms::wm2_running, 8, PropModeAppend,
                        reinterpret_cast<unsigned char*>(const_cast<char*>("")), 0);
        XMaskEvent(display(), PropertyChangeMask, &event);
        m_currentTime = event.xproperty.time;
    }

    return static_cast<Time>(m_currentTime);
}
```

[VERIFIED: `src/Manager.cpp:913-927`, quoted verbatim]

`XMaskEvent` blocks until a matching event arrives. It has no deadline and no
escape.

Callers on live interaction paths:

| Caller | Line | Path |
|---|---|---|
| `attemptGrab()` — `if (t == 0) t = timestamp(false);` | `src/Buttons.cpp:137` | every menu open, move and resize |
| `XSetInputFocus(..., timestamp(false))` | `src/Manager.cpp:339` | focus revert |
| `XSetInputFocus(w, ..., timestamp(false))` | `src/Manager.cpp:1175` | every focus change |
| `windowManager()->timestamp(false)` | `src/Client.cpp:316` | client state path |
| `ev.xclient.data.l[1] = ... timestamp(false)` | `src/Client.cpp:788` | WM_TAKE_FOCUS / protocol message |

[VERIFIED: `grep -rn 'timestamp(' src/ include/` output, this session]

Two ways this bites, both queue-ordering-dependent:

1. **It blocks.** The WM stops servicing MapRequest, ButtonPress, everything —
   while remaining alive and burning **no CPU**, so it is indistinguishable from a
   healthy idle loop from the outside.
2. **It swallows.** `XMaskEvent(PropertyChangeMask, ...)` matches a
   `PropertyNotify` on **any** window whose events this connection receives, not
   only the root append it just issued. Clients also have `PropertyChangeMask`
   selected — `src/Client.cpp:106` and `src/Client.cpp:1524` [VERIFIED: grep
   output] — so an unrelated client's property change can satisfy the wait and be
   **consumed and discarded**, never reaching `eventProperty()`. The converse
   leaves a later wait with nothing to match.

### Why it fits every observation the 04 halt recorded

| Observation from `08.5-04-SUMMARY.md` | Fit |
|---|---|
| "a different test each time", "exactly one failing test" per red run | A shared event-loop stall hits whichever case is running when the interleaving goes wrong. One stall, one casualty. |
| "A defect in the exec path cannot express itself as a geometry drag failure" | Correct — and this is not a defect in either case body. It is one tier down, in the loop both cases depend on. |
| Case 198: "a spawn that never happened, not a crash", 120.61 s = 45+45+15+15 | `menu()` dispatches `spawn()` after the loop; `attemptGrab` on that path calls `timestamp(false)`. A stall means no spawn and no sentinel, with the WM still alive — and `CHECK(fixture.wmAlive())` passed. |
| Case 93 failed at `REQUIRE(frame != 0L)`, `tests/test_wm_geometry.cpp:1492`, in **8.35 s** | `mapClientAndAwaitFrame()` polls for a reparent with an `8000` ms deadline [VERIFIED: `tests/test_wm_geometry.cpp:195` — `}, 8000);`]. 8.35 s is that deadline expiring. **The drag never ran.** A stalled loop services no MapRequest. |
| 0 of 12 in isolation, 1 of 5 loaded | An isolated run has a quiet display and a near-deterministic event sequence. Interleaving is what varies under a 313-case run. |
| The T-8-SHELL security half failed 0 of 5 | Consistent: a stall suppresses *actions*, it does not cause an unwanted shell evaluation. |

**Important correction to the record.** `08.5-04-SUMMARY.md` and the
flake-measurement README both describe case #93 as "an interactive drag". It is
not. Run 2's log shows it failing at `tests/test_wm_geometry.cpp:1492`,
`REQUIRE( frame != 0L )`, `assertions: 5 | 4 passed | 1 failed` — the failure is
in `mapClientAndAwaitFrame()`, **before the first `driver.click()`**
[VERIFIED: `evidence/gates/flake-measurement/build-all-debug-run2.log:248-282`].
This matters: it means the two failures are *more* alike than the halt record
thought. Both are "the WM did not act on a request", neither is an input-synthesis
problem, and **`dragSettle()`'s 90 ms is not implicated at all.** A fix plan that
starts by widening drag spacing would be chasing a symptom that was never there.

### The one thing that currently prevents attribution

Case 198 **captures the WM's stderr and then throws it away.** The `INFO` guard is
inside the lambda; the assertions that fail are outside it:

```cpp
        INFO("wm stderr:\n" << fixture.wmStderr());
        CHECK(fixture.wmAlive());
        ...
        return instance;
    };
    ...
    CHECK(shellWindow != None);
    CHECK(shellInstance == "shellmarker");
    CHECK(shellSentinel);
```

[VERIFIED: `tests/test_wm_runtime.cpp:1512-1536`, quoted verbatim]

Catch2's `INFO` is scoped: the message is attached only to assertions that fail
**while the guard is alive**. The lambda returns, the guard dies, and the three
CHECKs at 1534–1536 report with no message. This is visible in the evidence:
run 1's case-198 failure block shows the three expansions and **no** `with
message:` section, while run 2's case-93 failure — whose `INFO` is in the same
scope as its `REQUIRE` — prints the full WM banner
[VERIFIED: `build-all-debug-run1-FAILED.log:473-486` vs
`build-all-debug-run2.log:262-278`].

**This is the cheapest single change in the whole phase and it is a prerequisite
for honest attribution.** Hoist the WM stderr out of the lambda (return it, or
declare the `INFO` in the enclosing scope) and the next red run says, from a
committed log, whether the WM logged anything at all.

### Fix mechanisms for the defect itself, ranked

1. **Narrow the match *and* bound the wait** (recommended). Replace the bare
   `XMaskEvent(PropertyChangeMask, ...)` with a deadline-bounded predicate wait
   that matches only `PropertyNotify` on `m_root` with `atom == Atoms::wm2_running`.
   This closes both failure modes at once — the block and the swallow. On timeout,
   fall back to `CurrentTime` and log once to stderr with the `wm2: ` prefix.
   *Reversibility: easy, one function.*
2. **Do not invalidate the cache every iteration.** `src/Events.cpp:20` sets
   `m_currentTime = CurrentTime` unconditionally; the two places that already set
   it from a real event timestamp (`src/Events.cpp:540`, `src/Buttons.cpp:164`)
   show the better pattern. Narrower change, but it only reduces the *frequency*
   of the blocking branch rather than removing the unbounded wait. **Do both, or
   do (1); do not do (2) alone.**
3. **Widen a test deadline.** Explicitly rejected — see "Tier misassignment to
   watch for", above.

### One latent defect found on the way, worth recording

`m_currentTime` is declared `int m_currentTime;` [VERIFIED: `include/Manager.h:215`]
and initialised `m_currentTime(-1)` [VERIFIED: `src/Manager.cpp:79`], while X

## Common Pitfalls

### Pitfall 1: Re-running a red gate until it is green, and committing that

**What goes wrong:** the bundle certifies a run that needed retries.
**Why it happens:** the retry is one keystroke and the failure looks like noise.
**How to avoid:** `08.5-04-PLAN.md:125` already forbids it and 04 obeyed it. The
rule survives into this phase unchanged. The *after* measurement is a rate over
consecutive runs, not a single green log.
**Warning signs:** a summary that reports one green run and no rate.

### Pitfall 2: Ruling out a *case* and believing you ruled out a *defect*

**What goes wrong:** `[wm_menureopen]` fired 0/5, so deferred item 12 was
correctly excluded — but "the tagged case did not fail" and "the underlying defect
did not fire" are different claims. Deferred item 17's `findOpenMenu()`
first-viewable-child fallback, for one, can express through *any* case using the
unverified `openRootMenu()`/`selectFirstMenuEntry()` pair rather than through the
case named after it.
**Why it happens:** the deferred-items list is indexed by symptom, not by
mechanism.
**How to avoid:** attribute by mechanism (a stack, a log line), never by tag.
**Warning signs:** the phrase "this is the known intermittent" with no log line
beside it.

*Note for the planner:* `tests/test_wm_runtime.cpp` carries **two generations** of
menu helper. The verified pair (`openRootMenuVerified()` at :2977, retries 5×;
`nudgeUntil()` at :2948, polls until an observed predicate holds) is used by 6
call sites; the unverified pair is used by 5, **including case 198 at :1502-1503**
[VERIFIED: `grep -c` and `grep -n` over `tests/test_wm_runtime.cpp`, this session].
Migrating case 198 to the verified pair is a legitimate, cheap robustness
improvement — but it is **not** the flake fix and must not be presented as one. It
would mask the WM-tier defect. If it is done at all, do it *after* the fix is
measured, in a separate commit.

### Pitfall 3: Fixing the harness because it is easier than fixing the WM

**What goes wrong:** `dragSettle()` goes from 90 ms to 300 ms, the gate greens,
and a user on a busy VPS still loses their window manager for an unbounded
interval.
**Why it happens:** the harness is test code and feels safe to change.
**How to avoid:** the corrected reading of case #93 removes the excuse — it failed
in `mapClientAndAwaitFrame()`, before any drag, so drag spacing was never
implicated.
**Warning signs:** a diff whose only change is a larger number in a `sleep_for` or
a `constexpr int k*Ms`.

### Pitfall 4: Measuring "after" on a differently-loaded machine

**What goes wrong:** the before-rate (2/5) and the after-rate are taken under
different host conditions and compared as if they were commensurable.
**Why it happens:** this workstation is genuinely busy — measured this session:
load average 7.12 on 8 cores, 305 MB free of 32 GB, **swap 8191/8191 MB fully
consumed**, 10 logged-in users [VERIFIED: `uptime`, `free -m`, `nproc`].
**How to avoid:** record the host condition beside every rate. `uptime`, `free -m`
and the `Xvfb` orphan count, captured into the log immediately before each run.
Note also that total suite wall-time across the five 04 runs spans 227.80 s to
322.41 s — a 41% spread [VERIFIED: `grep -h 'Total Test time'` over the five logs]
— and that it does **not** cleanly correlate with the red runs (red: 322.41 s,
241.37 s; green: 309.22 s, 227.80 s, 228.06 s). Do not claim a load correlation
this evidence does not support.
**Warning signs:** an after-rate with no host-condition line beside it.

### Pitfall 5: A guard that has never been observed failing

**What goes wrong:** `grep -c 'validation pending'` == 0 passed against a file
that had never contained the string, and a blocker-grade gap survived a full
verification pass.
**Why it happens:** a positive-looking check is assumed discriminating.
**How to avoid:** plan 08.5-03 established the remedy and it is now house style —
run every guard against the pre-edit state, record it failing, then run it after.
Its summary records the before/after readings in a table.
**Warning signs:** an acceptance criterion with no "prints N before this task"
annotation.

### Pitfall 6: Attributing before measuring

**What goes wrong:** the hypothesis in this document is compelling and is
therefore dangerous. It is `[ASSUMED]`.
**How to avoid:** the fix plan's first task produces the log line. Only the task
*after* that may state a cause.
**Warning signs:** a plan whose first task is the fix.

## Architecture Patterns

### Pattern 1: Measure the rate, then attribute the cause, then fix — in that order

**What:** three separate steps, each with its own committed artifact.
**When to use:** any intermittent at a release gate.
**Why here:** 04 did step 1 and correctly refused to do step 2 without evidence.
This phase does steps 2 and 3. Collapsing them re-creates exactly the
attribution-by-assumption the halt record avoided.

### Pattern 2: Held evidence lives in a subdirectory that names what it is not

**What:** `evidence/gates/flake-measurement/README.md` opens with "**This
directory is not the success-criterion-7 gate bundle.**"
**When to use:** whenever a partial capture must be committed.
**Why:** the absent bundle stays visibly absent and a later reader cannot mistake
a partial capture for the record. Established by 04; keep it.

### Pattern 3: A guard is observed failing before it is trusted

Established by 08.5-03 (see Pitfall 5). Every acceptance criterion in the fix plan
should carry its pre-task reading.

### Pattern 4: A diagnostic belongs in the product, captured by the harness

The WM writes `wm2: `-prefixed diagnostics to stderr; `WmFixture` captures child
stderr to a file and exposes it via `wmStderr()`. Both halves exist. The pattern
is to add the trace to the product and let the existing capture carry it into
evidence — not to build a parallel observation channel in the test.

### Anti-Patterns to Avoid

- **Widening a deadline to green a gate.** Tier misassignment; see Pitfall 3.
- **Adding `RUN_SERIAL` / `RESOURCE_LOCK` "to be safe".** Inert under a serial
  gate, and it would leave a false record that parallelism was investigated as a
  cause when it was ruled out by reading one line of the gate script.
- **Deleting the flake-measurement directory once the gate is green.** It is the
  *before* half of the fix's evidence.
- **Silencing the intermittent by migrating case 198 to the verified menu
  helper.** Legitimate on its own merits, but it would mask the WM-tier defect and
  destroy the measurement. Separate commit, after the fix, if at all.

### Recommended plan shape

Three plans, or one plan with a hard internal stop after task 1:

1. **Instrument and attribute.** Stderr trace at the blocking branch; fix case
   198's `INFO` scope; sweep orphaned `Xvfb` by PID and record the host condition;
   run the debug gate until a red run is captured **with** the WM stderr in the
   failure output. Deliverable: a committed log that either confirms or refutes
   the hypothesis. **If it refutes it, stop and re-plan** — that is a good outcome
   and cheaper than the alternative.
2. **Fix and re-measure.** Bound and narrow the wait. Re-run the debug gate enough
   consecutive times to make a "green in one shot" claim mean something against a
   measured 40% red-run baseline (see Validation Architecture for the sampling
   arithmetic). Deliverable: an after-rate with its host condition beside it.
3. **Capture** (this is `08.5-04` retried) **then record** (`08.5-05`, already
   written).

### Sampling Rate — and the arithmetic that makes the after-claim mean something

This is the part that matters most, because the phase's central claim is
statistical and the baseline is measured.

**Baseline:** 2 red of 5 runs → an observed red-run rate of **0.40**
[VERIFIED: `evidence/gates/flake-measurement/README.md`, per-run table]. Five
observations is a small sample; the honest reading is "somewhere around 40%, with
wide uncertainty", not "exactly 40%".

**What a run of N consecutive greens buys.** If the true post-fix red-run rate
were still `p`, the probability of N consecutive greens is `(1-p)^N`:

| N consecutive green runs | Probability if p = 0.40 (unfixed) | Probability if p = 0.10 (mostly fixed) |
|---|---|---|
| 3 | 0.216 | 0.729 |
| 5 | 0.078 | 0.590 |
| 8 | 0.017 | 0.430 |
| 10 | 0.006 | 0.349 |

**Recommendation: 8 consecutive green full debug runs** as the phase gate. At the
measured baseline that is a ~1.7% chance of occurring by luck, which is a real
claim; and at ~4 minutes per run it costs roughly half an hour of wall time, which
is affordable. **5 is the floor** if time is short — say so explicitly and state
the 7.8% figure rather than implying certainty. **3 is not enough** and a plan
proposing it should be sent back: 21.6% is one run in five.

Sampling schedule:

- **Per task commit (during the fix):** `ctest --test-dir build/debug -L '^wm_config_runtime$' --no-tests=error` plus the two new bounded-wait cases. Seconds, not minutes.
- **Per wave merge:** one full `bash scripts/gates/build-all.sh debug`. ~4 min.
- **Attribution gate (end of plan 1):** one red run captured **with** WM stderr in the failure output, committed.
- **Fix gate (end of plan 2):** 8 consecutive green `build-all.sh debug` runs, each with `uptime` / `free -m` / orphan-count recorded beside it, committed as a table.
- **Phase gate (plan 3 = 04 retried):** all three trees plus static analysis green in **one** pass, at the final commit, captured into `evidence/gates/` with `PROVENANCE.txt`.

| Claim | Artifact that makes it checkable |

| "The WM entered the blocking branch" | A `wm2: `-prefixed stderr line in a committed red-run log, inside the failing case's `with message:` block |
| "The failure rate dropped" | Two per-run tables — the existing `flake-measurement/README.md` (before) and a new one (after) — each with exit codes and host conditions |

## Open Questions

1. **Does the WM actually enter `timestamp()`'s blocking branch during a red run?**
   - *What we know:* the branch is reachable on every loop iteration and sits on
     the grab and focus paths both failing cases traverse.
   - *What's unclear:* whether it fires, and for how long.
   - *Recommendation:* plan 1's stderr trace. One red run settles it. **This is
     the phase's pivot; nothing downstream should be planned as if the answer
     were known.**

2. **If it is not the cause, what is?**
   - *Next candidates, in order:* (a) deferred item 17's `findOpenMenu()`
     first-viewable-child fallback reaching case 198 through the unverified menu
     helper — which would explain 198 but not 93; (b) fixture teardown racing the
     next fixture's display reservation; (c) host memory pressure with swap
     exhausted making `fork`/`exec` latency unbounded.
   - *Recommendation:* record them in the plan as named alternates so a refutation
     has somewhere to go.

3. **Does the ASan tree carry the same rate?** 04 never ran it — "The release and
   asan trees were never run." The sanitizer widens every timing window, and the
   comment at `tests/test_wm_runtime.cpp:2955-2957` records a defect measured at
   "2 failures in 20 ASan runs … and 0 in the debug tree".
   - *Recommendation:* measure the ASan tree's rate **once, before the fix**, so
     the after-capture's three-tree pass is not the first ASan observation in the
     phase. One run, ~10 minutes.

4. **Should `int m_currentTime` be widened to `Time` in this phase?** It is a real
   defect with a documented sibling.
   - *Recommendation:* record it, fix it **after** the flake measurement closes,
     so the before/after comparison isolates one change. If the planner disagrees,
     the counter-argument is that both changes live in the same function and
     splitting them costs a commit — acceptable either way, but state which was
     chosen and why.

5. **How many consecutive green runs will the operator actually fund?** The
   arithmetic above prices 3, 5, 8 and 10.
   - *Recommendation:* put the table in front of the operator rather than picking
     silently. This is exactly the kind of call that produced ruling B.
