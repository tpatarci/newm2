<objective>
Dismember the menu open-paint-sample path into separate program units, each with
its own verdict, so that the residual `Menu background colour reaches the menu
opened by a real root click` flake is ATTRIBUTED to a named unit rather than
measured.

**The operator's instruction, and why a repeat count does not satisfy it.**
`08.5-11` recorded that after the event-loop fix three full-suite runs gave two
clean runs and one failure of this case, its sampled menu unpainted, and that
whether the round changed that behaviour is a question it does not answer. The
instruction is not to run it more times. It is to break the processing into at
least two separate units so the source is smoked out. A rate tells us the case
reddens; it cannot tell us which of four fused stages produced the red.

**What is fused today.** `openRootMenu()` (`tests/test_wm_runtime.cpp:697-724`)
runs four stages behind one boolean:

1. `findOpenMenu()` — has the window manager mapped a menu?
2. `serverRect(...) && w > 1 && h > 1` — has the server realised its geometry?
3. `captureRoot(d, rect).size() >= 2` — a stand-in for "has it been painted?"
4. the caller then samples with `captureRoot()` and takes a dominant pixel.

Stage 3 is wrong on its own terms. It asks only for **two distinct pixel values
anywhere in the rectangle**. A half-drawn menu satisfies it. Root pixels
bleeding through an unfilled window satisfy it. A menu painted in entirely the
wrong colour satisfies it. It is a non-specific negative standing where a
positive criterion belongs.

Stage 4 never reads the menu. `captureRoot()` calls
`XGetImage(d, DefaultRootWindow(d), ...)` at screen coordinates, so it reads the
framebuffer where the menu is expected to be, with compositing and stacking in
between.

**And production has a real, matching hazard.** The outer menu is painted ONLY
from the `Expose` arm of the modal loop: `outerDrawn` starts false
(`src/Buttons.cpp:312`), is set true at exactly one site (`:543`), and guards
every draw (`:396`). A lost or misrouted `Expose` leaves the rows permanently
unpainted, and nothing retries. The same loop already discards `Expose` for any
other window — the defect `08.5-11` recorded against `src/Buttons.cpp:530`.

So the flake has at least three candidate homes, and today's test cannot
distinguish them. This round separates them.

**The units.**

- **Unit 1, production — `include/MenuPaint.h`.** The Expose-to-paint decision,
  lifted out of the modal loop into a pure function returning a named target:
  outer, submenu, foreign, or none. The silent fallthrough becomes an assertable
  value.
- **Unit 2, test instrument — `tests/support/PixelVerdict.h`.** The
  paint-completion decision as a pure function over a histogram, returning a
  named verdict — no pixels, uniform fill, mixed content, or painted-as-expected
  — instead of a pixel count.
- **Unit 3, the discriminator.** Two independent captures of the same instant:
  the root-framebuffer readback the test uses today, and a direct readback of
  the menu window. Their agreement partitions every failure.

**The partition, fixed before the measurement.** Given both captures at one
instant, exactly one bucket applies:

| Root readback | Direct menu readback | Attribution |
|---|---|---|
| disagrees with direct | — | the READBACK PATH — a test-instrument defect |
| agrees, wrong colour | agrees, wrong colour | PRODUCTION did not paint — check whether an `Expose` was delivered |
| agrees, right colour | agrees, right colour | the COMPLETION PREDICATE let the sample run early |

There is no fourth bucket. Whichever fires, the round names a unit.

**Why one of these units cannot flake at all.** `test_menupaint` opens no
display, spawns no window manager, takes no fixture and reads no clock. Its
inputs are synthetic histograms and integers. Whatever it reproduces, it
reproduces identically on every run and every host — which is what makes it
evidence rather than a sample.

**What this round does not claim.** It does not claim the suite is now reliable.
That is a rate; Task 4 reports counts with their arithmetic and nothing more.
</objective>
