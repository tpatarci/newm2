<objective>
Bound and narrow the window manager's timestamp property wait, prove both halves
with cases that redden when the production branch they name is mutated, and
re-measure the debug gate's red-run rate against the 0.40 baseline plan 08.5-04
recorded.

Purpose: `WindowManager::timestamp()` takes an unbounded blocking wait on the
window manager's only thread, and the mask it waits on matches a `PropertyNotify`
on any window this connection receives events for — not only its own root append.
Both halves are defects on their own terms for a window manager that has to run
in 512 MB on a VPS: the first can stall the event loop for an unbounded interval
while burning no CPU and looking exactly like a healthy idle loop, and the second
can consume and discard a client's property change before `eventProperty()` ever
sees it, which is the input a title rule folds on (D-8.5-02, D-8.5-03).

Output: a deadline-bounded, predicate-narrowed wait that degrades to a warning
and `CurrentTime` rather than to a stall; two `[wm_timestamp]` regression cases,
each mutation-checked in both trees; a mutation row that wedges the event loop on
demand, converting the research's `[ASSUMED]` mechanism into something
demonstrated; and an after-table of ten consecutive green full debug runs with
their host conditions, column-comparable with the before-table.

Sequencing: depends on 08.5-06, whose attribution verdict and operator ruling
gate Task 1. Plan 08.5-08 captures the criterion-7 bundle after this plan, and the
already-written 08.5-05 consumes that bundle last.
</objective>

  <behavior>

    - When one is not queued, `timestamp(false)` waits for a `PropertyNotify` on `m_root` whose atom is `Atoms::wm2_running`, and for nothing else, for at most the named bound.

  <action>
Replace the wait, keep everything the instrumentation reports.

**The predicate.** Add a file-scope predicate function in `src/Manager.cpp` matching the file's existing static-helper convention (`makeCursor()` is the shape precedent) that returns true only for a `PropertyNotify` whose window is the root and whose atom is `Atoms::wm2_running`. The predicate takes the `XPointer` argument Xlib's check-form-with-predicate call passes, and the root window is handed through it rather than read from a global.

**The bound.** A named `constexpr` millisecond constant in the same translation unit, with a comment stating why the value was chosen: the wait is satisfied by a round trip on a local socket, which is sub-millisecond even on a host with a load average above its core count, so a bound in the low hundreds of milliseconds is three orders of magnitude of headroom and still an order of magnitude below the harness deadlines a stall currently blows through. 250 ms is the recommended value; if a different one is chosen, state the reasoning in the same comment rather than leaving a bare number.

**The wait itself.** Replace the bare `XMaskEvent(display(), PropertyChangeMask, &event)` with a deadline loop built from what this repository already uses:

- compute the deadline once, from `std::chrono::steady_clock`, the way `pollUntil()` does;
- try the check-form-with-predicate read; if it returns an event, done;
- otherwise `XFlush()`, then `poll()` on `ConnectionNumber(display())` for the remaining time, retrying on `EINTR` exactly as `nextEvent()` does at `src/Events.cpp:194`;
- loop until the predicate matches or the deadline passes.

**Do not** build a `select()`, thread, `alarm()` or signal scaffold, and do not add a dependency: the project must stay lightweight for VPS use and the idiom is already here twice.

**The timeout branch.** On expiry: leave `m_currentTime` at `CurrentTime` so the next call retries rather than caching a wrong value, print one `wm2: warning: timestamp: ` line naming the state and the elapsed bound as an integer — a state word and a number, no window id, atom name or title (threat T-8-REMOTE) — and return `CurrentTime`. Rate-limit the warning the way plan 08.5-06 rate-limited its foreign-match line, so a pathological host produces one line rather than a flood that changes the timing it is reporting on. Never `fatal()`: `include/Border.h:183-184` already states this project's position that graceful degradation beats killing the window manager, and a caller receiving `CurrentTime` gets the same value every X client uses when it has no better timestamp.

**What must not change.** The `XChangeProperty` append stays — it is what causes the event the predicate waits for. The assignment from `event.xproperty.time` on the success path stays. Every counter and every diagnostic line from plan 08.5-06 stays, because the two new cases in Task 2 assert on them and the after-table in Task 3 reads them.

**What is deliberately not fixed here.** `m_currentTime` is a signed `int` holding an X `Time`, and `src/Buttons.cpp:128-136` documents exactly what that does after ~24.8 days of server uptime on a VPS droplet that is left running — which is this project's whole target. It is a real defect and it lives in this same function. It is **not** fixed in this plan, because two changes in one function make the before/after rate measurement ambiguous about which one moved it. Record it in the summary as a named, deliberate deferral with the phase that should take it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client windows -> the window manager's event queue | Clients carry `PropertyChangeMask`, so their property events arrive on the same connection the timestamp path reads from |

| Measured rate -> release claim | A rate becomes "the gate is green in one shot" only if no run was omitted or retried |
