## Phase Boundary

Close the three requirements Phase 8 left Pending — RULES-01, XDIS-05, TEST-08 —
so that v1.0 ships with **zero requirements silently unmet**. Everything here is
finishing work on promises already made; no new capability is invented.

Requirements: RULES-01, XDIS-05, TEST-08.

**In scope:**

- WM_NAME (title) matching for window rules, plus the config key rename that
  makes the three match keys mean what they say
- Reading `_NET_WM_NAME` for the window title, because the WM currently reads
  only the legacy `WM_NAME` and a title rule built on that alone would be born
  half-dead (see D-8.5-02)
- Validating the two remote-desktop targets Phase 8 recorded as deviations:
  TightVNC and X2Go
- Running the User Interaction Checklist once as a per-item pass/fail table
- Retiring or restating D-8-TIGHTVNC and D-8-X2GO on the evidence produced

**Out of scope:**

- Re-folding rules when a window's title changes after it is mapped (D-8.5-03 —
  goes to the v1.1 backlog, deliberately)
- Gesture/input test coverage (v1.1 backlog — real, but not a requirement and
  not v1.0 work)
- Anything the Config GUI needs (Phase 9)
- Multi-monitor, multi-desktop, core X fonts — unchanged phase-8 exclusions

## Why this is a phase and not a fold into Phase 9

RULES-01 changes the **config surface** that Phase 9's GTK tool will expose and
edit. A GUI built against `rule-match-name` and then re-pointed at
`rule-match-instance` mid-phase is rework that buys nothing. Land the surface
first; let Phase 9's record be about the GUI.

<decisions>
## Implementation Decisions

### D-8.5-01 — Rename the rule match keys, once, before v1.0

`rule-match-name` matches the WM_CLASS **instance name** while its name says
WM_NAME. That mismatch is what put a false promise into `docs/RELEASE-NOTES.md`
and needed correcting in `66591ec`. The keys become:

| Key | Matches |
|---|---|
| `rule-match-class` | both WM_CLASS fields — the forgiving one, unchanged |
| `rule-match-instance` | the WM_CLASS instance name (was `rule-match-name`) |
| `rule-match-title` | the window title — new |

**Clean rename, no deprecated alias.** v1.0 has not shipped, so nothing is owed
to an old spelling; an alias for a key with no users outside this machine is
permanent surface bought for nothing. The cost is visible and one line wide: an
existing config using `rule-match-name` gets the parser's existing
`unknown config key` warning. Renaming is free today and breaking the day after
v1.0 ships. — **Reversibility:** trivial before release, expensive after.

### D-8.5-02 — Read `_NET_WM_NAME` before `WM_NAME`

**Finding, verified 2026-08-30:** `src/Client.cpp:109` reads the window title
with `getProperty(XA_WM_NAME)` and nothing anywhere reads `_NET_WM_NAME` for a
client. `Atoms::net_wmName` is interned (`src/Manager.cpp:166`) and used only to
name the WM's own check window (`src/Manager.cpp:753`).

A title rule keyed on that alone would be a control that looks available and
silently does nothing for any client that sets only the EWMH property — which is
precisely the defect class the whole of Phase 8 was spent removing, and exactly
the shape of the four release-note defects the verifier found in `66591ec`.

So the title read becomes EWMH-first with the ICCCM property as fallback. This
is scope beyond a literal "add a title field to the facts struct", and it is
deliberate: shipping the literal version would satisfy the requirement's words
and not its promise. — **Reversibility:** easy, one function.

**Consequence to prove, not assume:** `m_name` also feeds `setLabel()` and the
sideways tab. Changing where it comes from changes what the tab paints. That must
be pinned by a test, not eyeballed.

### D-8.5-03 — Rules fold once, at manage time. Title rules included.

A rule matching on title matches the title **as it stands when the window is
mapped**. The WM will not re-apply position or size when a title later changes:
re-folding would make windows jump when a document is renamed or a tab is
switched, which is worse than the gap it closes. Openbox and peers behave the
same way.

This is a legitimate semantic **only if it is stated**, so it is stated in three
places: the requirement text, the release notes, and a comment at the fold.
Re-fold-on-title-change goes to the v1.1 backlog.

### D-8.5-04 — X2Go is validated, not descoped

**This reverses the plan of record, on measurement taken 2026-08-30.** See
"What changed since the handoff" below. `nxagent` is installed, runs headless
nested on an Xvfb, and the whole capture takes about two minutes with no human
in the loop. The premise that X2Go validation "costs a human session" is false.

Both remaining targets are therefore validated rather than amended away, and
XDIS-05 is met as written — four targets, four transcripts — instead of met as
reworded. No requirement amendment is needed for XDIS-05.

### D-8.5-05 — The interaction checklist is run as a table, per item

TEST-08's shortfall is the **form of the record**, not the amount of testing.
Two manual passes happened; the second produced a general verdict. A per-item
pass/fail table with tester name and date is the deliverable. In a showcase
project the evidence bundle is a first-class artifact, which is why this is worth
one more sitting after the operator already declared testing sufficient.

**Fallback if the operator declines the sitting:** transcribe the two existing
passes into the table with `verified in pass 1/2` citations and mark the rest
`not exercised`. Do not start there — the two manual passes produced three
defects between them, a rate that argues for running it rather than transcribing
it.

### D-8.5-06 — Deviations are retired on evidence or restated with a fresh reason

D-8-TIGHTVNC and D-8-X2GO each carry a follow-up saying exactly this. A deviation
that survives the evidence that was supposed to close it becomes a permanent gap
by default. Whichever way each one lands, it does not stay as written.

</decisions>

<what_changed>
## What changed since the handoff was written

The handoff (`08-.../.continue-here.md`, commit `5c95258`) recorded a decided
shape in which X2Go was moved to a v1.1 requirement and XDIS-05 amended to name
three targets. **Three facts measured on 2026-08-30 falsify the premise that rested
on**, and all three are cheap to re-verify:

1. **`x2goserver 4.1.0.3-5` is installed on this host**, along with
   `x2goserver-x2goagent` and `nxagent 2:3.5.99.26-5`. `/var/log/dpkg.log`
   stamps the install at **2026-08-29 17:43** — during Phase 8's own manual-pass
   window. The evidence index and `08-14-SUMMARY.md` both say "`x2goserver` was
   never installed"; that sentence is now false and is corrected in Plan B.

2. **`nxagent` runs headless as a nested server** — `DISPLAY=:<host> nxagent -R
   :<nested>` over an Xvfb — needing no X2Go client, no SSH session and no human.

3. **The extension surface D-8-X2GO calls untested is present and measured.**
   On nxagent: SHAPE, RANDR, RENDER, XTEST, XKEYBOARD all advertised, 23
   extensions total. The window manager was run against it: it started, detected
   all three extensions, published the full `_NET_SUPPORTED` list, framed an
   `xclock` at the standard `+24+8` client offset, and appeared in
   `_NET_CLIENT_LIST`. `scripts/capture-display-capabilities.sh :<nested> <label>`
   produced all three transcript files unmodified.

The probe artifacts were **deleted, not committed**: evidence belongs to the
commit that Plan B captures it at, with the provenance header the script writes
and the T-8-REMOTE title screening applied.

**What this does not settle.** A nested nxagent on a local Xvfb is not the same
thing as X2Go over a network link with its compression proxy in the path — which
is the layer D-8-X2GO is actually worried about. Plan B captures the nested
transcript as the automated floor and puts the real client session in the human
sitting alongside the interaction checklist. The distinction is recorded in the
transcript, not smoothed over.

</what_changed>

<carry_forward>
## Carry-forward that will cost time if forgotten

### Test anti-patterns — read before writing any test in this phase

| Anti-pattern | Severity |
|---|---|
| Writing a test that passes without mutating the branch it names | **blocking** |
| Running the mutation table only in the debug tree | **blocking** |
| Tight-loop settles in process-level tests | **blocking** |

- **Every plan from 08-07 through 08-14 found a test that did not test its own
  name.** Delete or invert the production branch and confirm *that* case reddens.
- **Mutate under ASan as well as debug.** 08-12 and 08-13 each found mutations
  green in debug and fatal under the sanitizer.
- **Interactive-input tests need wall-clock spacing, not `pumpWm()`.**
  `Client::move()`'s loop drains every queued event in one sweep and dispatches
  only the last, so an unspaced `ButtonRelease` is drained alongside the motions
  and the drag silently does nothing. Use `dragSettle()` in
  `tests/test_wm_geometry.cpp` (90 ms, clears the loop's `poll(50ms)`).
- **Guard against vacuous passes.** A frame press is dropped unless the client is
  already active, so a drag test can pass having done nothing at all. Use
  `awaitActive()` plus a "did it actually move" `REQUIRE`. Measured 1-in-4
  vacuous before that guard was added.
- **`findFrameChild()` separates tab from button by SIZE, not origin** — they
  share `(0,0)` since the button-target change in `43fb24b`.

### Known flake

**Item 17:** `[wm_menureopen]` fails intermittently with the menu simply never
appearing. Measured over 12 isolated runs each: 11/1 with the menu rewrite, 11/1
with an added settle, and **11/1 against the pre-existing two-loop `menu()`** —
equal rate on the old code, so the rework did not cause it. **Treat a single such
failure as this known flake only after reproducing it in isolation, never by
assumption.**

### Deferred items still open

**5** (bare `ctest --test-dir build/asan` is red — LSan suppressions are not
wired into the Catch2 binaries; use `scripts/gates/build-all.sh asan`),
**9**, **10**, **12**, **13**, **17**. Resolved in Phase 8: 6, 7, 8, 11, 14.

### Two operator reports left open and unexplained, deliberately

- **"Malformed window dressing"** — reported, NEVER REPRODUCED, cause unknown.
  The leading hypothesis (a destructive tab-height clamp) was ruled out by
  measurement. The drag clamp in `a5a105c` may have removed only its
  precondition. **Do not record as resolved.**
- **Sideways tab-label geometry nit** — "some geometry adjustments will be
  needed", never pinned to specifics across three passes. Cosmetic, open.

### Operational gotchas

- **Never `pkill -f "<pattern>"` for X servers or the WM** — the pattern matches
  the killing command's own wrapper and takes the shell down with it. This bit
  again on 2026-08-30. Kill by PID.
- The root menu is **Button1**; Button3 is circulate.
- The host carries a long tail of orphaned `Xvfb` servers from test runs
  (`/tmp/.X11-unix/` had 23 sockets on 2026-08-30). Pick fresh display numbers;
  do not assume a low number is free.
- GSD isolation: `worktree.base-check` reports `shouldDegrade: true` (#683), so
  `ISOLATION=none`. The run-scoped sentinel expires between dispatches —
  re-persist immediately before every `Agent()` call.

<open_questions>
## Open questions for the planner

1. **Does changing the title source (D-8.5-02) change what the tab paints for any
   client under test?** It should only add titles that were previously missing,
   but `setLabel()` consumes `m_name` and the answer must come from a test, not
   from reading the code.
2. **Does TightVNC's ancient `Xvnc` actually advertise RANDR and RENDER?** If it
   does not, that is the more interesting result: it exercises the XDIS-02/03/04
   fallback paths against a genuinely degraded server rather than against a
   forced env var, and it makes D-8-TIGHTVNC's "substantially overlapping
   extension set" rationale measurably wrong. Either outcome is worth having.
   Plan B must not treat a missing extension as a failure — the capture script is
   built on exactly that principle.
3. **If TightVNC or X2Go fails in ways the existing fallbacks do not cover**,
   8.5 grows by a fix plan. That trade was accepted when the validation was
   chosen over the amendment.
</open_questions>
