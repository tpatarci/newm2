<objective>
Bound and narrow the timestamp property wait, proving both halves with cases that
fail at the pinned round base and pass after the fix — then put the two decisions
this round's evidence forces in front of the operator.

**What is wrong, established by reading the source rather than by measuring runs.**
`WindowManager::timestamp()` obtains a server time by making a no-op property
change and waiting for the resulting `PropertyNotify`. Two defects:

*Unbounded.* The sentinel is a zero-length `PropModeAppend` (`src/Manager.cpp:923`).
Append requires the existing property's type and format to match; a foreign client
can replace `_WM2_RUNNING` with a different type or format — root properties are
owned by nobody — and the request then yields `BadMatch` and generates no
`PropertyNotify` at all. The non-blocking check at `:944` finds nothing, and the
blocking selector at `:959` waits **with no deadline**, uninterruptible by the
self-pipe. At startup the same error terminates the process instead; at runtime it
hangs.

*Over-broad.* Both selectors match any `PropertyNotify` on this connection —
irrespective of window, atom, or `send_event`. So the timestamp path consumes other
clients' notifications: a managed client's `_NET_WM_NAME` change is swallowed,
`eventProperty()` (`src/Events.cpp:535`) never runs, and the client's title
silently stops refreshing. It also accepts a **synthetic** `PropertyNotify`, so any
client can supply a chosen timestamp. And this is not merely a contention hazard —
it fires deterministically at startup, because `setupEwmhProperties()` (`:792`)
changes root properties after the property bit is selected (`:603`) and before
`timestamp(true)` runs (`:288`), so the first matching event is reliably an EWMH
notification rather than the sentinel.

**Its relationship to the round-3 ruling, stated precisely because the distinction
is the whole point.** Round 3 ruled `REFUTED` on the question of whether this path
explained an observed reparent hang, on the strength of five backtraces that named
the event loop's own poll and not this path. That ruling stands, untouched. This
plan establishes a *different* claim — that the code is wrong on its own terms —
by a *different* method. Not-observed is not absent, and it was that conflation
which held `08.5-07`, the plan that would have fixed this.

**What this round does not claim.** It does not claim the release gate is now
reliable. That is a rate, and this round measures none.
</objective>

Narrow the predicate and bound the wait. Both halves are required: narrowing alone
still permits an unbounded wait when the sentinel never arrives, and bounding alone
still steals other clients' events.

**Narrow.** Replace the mask match with a predicate accepting only the sentinel —
window is the root, atom is `_WM2_RUNNING`, `send_event` is false. Xlib's
predicate-based selectors exist for this and leave non-matching events in the
queue. Rejecting `send_event` is correctness, not hardening: any client can
synthesise a notification carrying a chosen time, and the current code takes it.

**Bound.** Give the wait a short, finite deadline with a defined fallback. Justify
its value on its own terms — a window manager blocked in a property wait is serving
no client, so the bound is chosen to be imperceptible to a user while leaving room
for a loaded server to answer. Do **not** justify it by reference to the 8000 ms
reparent deadline: that constant lives entirely under `tests/` and has no
production counterpart, and tying a production timeout to it would be a category
confusion. Record the fallback's use through the existing counter-and-stderr idiom,
adding to it rather than renaming anything in it. Neither value may be settable
from the environment.
  </action>
