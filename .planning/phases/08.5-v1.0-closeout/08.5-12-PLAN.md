<objective>
Make the timestamp path survive a hostile root property: it must not kill the
window manager at startup, must not wait forever at runtime, must not steal another
client's notification, and must not accept a forged one — each proved by a case
that fails at its pinned baseline and passes after the fix. Then put the two
decisions this round's evidence forces in front of the operator.

**What is wrong, established by reading the source rather than by measuring runs.**
`WindowManager::timestamp()` obtains a server time by making a no-op property
change and waiting for the resulting `PropertyNotify`. Three defects, not two:

*Fatal at startup.* The sentinel is a zero-length `PropModeAppend`
(`src/Manager.cpp:923`). Append requires the existing property's type and format to
match; a foreign client can replace `_WM2_RUNNING` with a different type or format
— root properties are owned by nobody — and the request then yields `BadMatch`.
During initialisation that error does not cause a hang at all: `errorHandler()`
reaches `if (m_initialising) { ... std::exit(1); }` at `src/Manager.cpp:416-419`
and **the window manager exits**. The constructor calls `timestamp(true)` at
`:288`, two lines before `m_initialising = false` at `:290`, so the entire sentinel
round trip happens inside that window. **Bounding the wait does not touch this
defect** — the wait is never reached.

*Unbounded at runtime.* The same `BadMatch` after startup generates no
`PropertyNotify`. The non-blocking check at `:944` finds nothing, and the blocking
selector at `:959` waits **with no deadline**, uninterruptible by the self-pipe.

*Over-broad, always.* Both selectors match any `PropertyNotify` on this connection
— irrespective of window, atom, `send_event` or `state`. So the timestamp path
consumes other clients' notifications: a managed client's `_NET_WM_NAME` change is
swallowed, `eventProperty()` (`src/Events.cpp:535`) never runs, and the client's
title silently stops refreshing. It also accepts a **synthetic** `PropertyNotify`,
so any client can supply a chosen timestamp. And this is not merely a contention
hazard — it fires deterministically at startup, because `setupEwmhProperties()`
(`:792`) changes root properties after the property bit is selected (`:603`) and
before `timestamp(true)` runs (`:288`), so the first matching event is reliably an
EWMH notification rather than the sentinel.

**Its relationship to the round-3 ruling, stated precisely because the distinction
is the whole point.** Round 3 ruled `REFUTED` on the question of whether this path
explained an observed reparent hang, on the strength of five backtraces that named
the event loop's own poll and not this path. That ruling stands, untouched. This
plan establishes a *different* claim — that the code is wrong on its own terms —
by a *different* method. Not-observed is not absent, and it was that conflation
which held `08.5-07`, the plan that would have fixed this.

**What this round does not claim.** It does not claim the release gate is now
reliable. That is a rate, and this round measures none.
</objective>
