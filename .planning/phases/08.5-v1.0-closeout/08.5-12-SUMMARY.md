# Phase 08.5 Plan 12: The timestamp path — three defects, four cases, two decisions Summary

This summary was written on 2026-09-05, after execution, from the plan's committed commits and `evidence/gates/timestamp/`. Tasks 1-2 were committed on 2026-09-01; Task 3 was written the same day but could not close until 2026-09-05 (see Execution history below); Task 4 and Task 5 completed 2026-09-05.

**`WindowManager::timestamp()` held three separate defects, established by reading `src/Manager.cpp` rather than by measuring runs: a zero-length `PropModeAppend` that a foreign client can turn into a `BadMatch`, which during initialisation reaches `errorHandler()`'s `std::exit(1)` and kills the window manager outright — not merely hangs it; the same `BadMatch` after startup leaves an `XMaskEvent` wait with no deadline and no way for the self-pipe to interrupt it; and both selectors match ANY `PropertyNotify` on the connection, deterministically consuming EWMH notifications at startup and accepting forged ones from any client. Round 3's `REFUTED` verdict, on whether this path explained an observed hang, stands untouched — this plan establishes a different claim (the code is wrong on its own terms) by a different method (source reading plus deterministic reproduction), and neither statement contradicts the other.**

This plan makes no rate claim anywhere in its record. It does not describe any result as curing an intermittent failure, and it does not describe any gate's post-fix state as reliable going forward. Every claim is a deterministic reproduction (a Catch2 case that fails at a pinned commit and passes at another) or a source-level read of `src/Manager.cpp` as it stood at a pinned commit. The standing arithmetic — 2-red-of-5 vs 0-red-of-10 gives p ≈ 0.095, clearing 0.05 needs 0 red of 16, detecting 0.40 → 0.20 at 80% power needs ~36 runs — is carried into every place this record is tempted to read a green run as more than what it is.

## What was built

- **Task 1** extracted the sentinel request, the four-field-capable predicate site and the wait out of `WindowManager::timestamp()` into a new header-only `include/TimestampWait.h`, copying the shape `08.5-11` established for `include/EventPump.h`. The extraction was a pure refactor: the request stayed the same zero-length `PropModeAppend`, the predicate still accepted any `PropertyNotify` irrespective of window/atom/`send_event`/`state`, and the wait still ignored its deadline argument and blocked indefinitely via `XMaskEvent`. All three defects were preserved on purpose, so Task 2's cases would have a real baseline. `timestamp()` was rewritten to call the three extracted entry points by name; no error trapping was added.
- **Task 2** pinned Task 1's tip as `PLAN_12_T1` (`0d5dc07c7f79fac3ab426554a97292726c879fa5`) — committed alone, first, because `ROUND_BASE` and `PLAN_11_TIP` both predate Task 1's deliberate change to `src/Manager.cpp` and a no-production-diff gate against either would fire on Task 1's own legitimate work. Four cases were added to `tests/test_eventloop.cpp`: `timestamp-survives-poisoned-property`, `timestamp-leaves-foreign-property-alone`, `timestamp-rejects-synthetic`, `timestamp-is-bounded`. `timestamp-is-bounded` runs the production wait in a forked child that the parent bounds and `SIGKILL`s, because a thread cannot be cancelled inside Xlib without leaving the connection's lock held. All four failed at `PLAN_12_T1`, captured to `red-before-fix.log` (exit 8, four of fifteen `eventloop`-labelled tests failing), and ten consecutive runs agreed. No production file changed in this task.
- **Task 3** fixed all three defects in `include/TimestampWait.h` and `src/Manager.cpp`: the sentinel is now a zero-length `PropModeReplace` whose type and format the code itself chooses (cannot mismatch, so no error trap was needed); the predicate now tests all four fields (root window, `_WM2_RUNNING` atom, `send_event` false, `state` `PropertyNewValue`), leaving non-matching events queued for `eventProperty()`; and the wait is now `XCheckIfEvent` plus `poll()` against a monotonic 250 ms deadline (`kTimestampWaitDeadlineMs`, compile-time, not environment-settable), returning `CurrentTime` and leaving the cache cold on expiry while recording the timeout through a new counter (`m_timestampWaitTimeouts`) alongside — never replacing — the existing 08.5-06 instrumentation. Written 2026-09-01 as commit `1fbf98d`; **blocked** there because the full debug suite failed one `[wm_menulabel]` case for a reason outside this plan's `files_modified` (see Execution history). Rebased onto `08.5-13`'s merged tip `afd3ec2` on 2026-09-05 as `57d5581`, where all gates re-ran clean: `build-all.sh debug` 329/329, `build-all.sh asan` 329/329 with no sanitizer findings, `NO-UNBOUNDED-SELECTOR` and `PREDICATE-NARROWED` both printed, `attribution/README.md` unchanged against `ROUND_BASE`, and a numeric-literal review found only the new 250 ms deadline and two new test constants (3000, `0x5E4713A9`) as additions, with the existing `100` unchanged and nothing widened.
- **Task 4** captured the full `build-all.sh debug` transcript to `green-after-fix.log` (100% passed, 0 failed, out of 329) and completed `evidence/gates/timestamp/README.md`: all three defects with their concrete failing interleavings (including the startup `exit(1)` route with line numbers), the before/after table for all four cases, ten agreeing `eventloop`-label runs (exit 0 × 10, 15/15 each), the relationship to round 3 stated without re-opening it, a "What this does not establish" section carrying the standing arithmetic, and an execution note explaining the 2026-09-01 block and the 2026-09-05 rebase.
- **Task 5**, a `checkpoint:decision` gated `blocking-human`, presented two decisions and wrote nothing until they were answered. Both were answered 2026-09-05; see below.
