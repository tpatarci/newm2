<objective>
Fix the event loop's readiness ordering, the unguarded `XNextEvent()` on bare
`POLLIN`, the unbounded and over-broad timestamp property wait, and the
never-consumed exit flag — each with a deterministic test that fails before the
fix and passes after it. Record the deductive findings, and triage every
secondary defect the audit surfaced.

**Why this round exists, and why it is shaped differently from the three before
it.** Plans 08.5-06, 08.5-09 and 08.5-10 tried to attribute a reparent wedge
statistically: eight full-suite samples, then five hang-time backtraces, then a
two-arm intervention over 8000 window maps producing 129 trips and 40 evidence
bundles. That chain cost three rounds and three operator rulings and ended
without a mechanism. A line-by-line read of `WindowManager::nextEvent()` against
the Xlib contract, plus one forty-line probe, produced the mechanism and a
deterministic reproduction in seconds.

An X11 event loop is a deterministic system. Its defects are provable by reading
it and reproducible on demand. Verifying one stochastically is a category error,
and this round replaces that instrument rather than taking a fourth turn with it.

**The defect, stated as the measurement found it rather than as it was
hypothesised.** The earlier account held that events were stranded in libxcb's
transport queue, invisible to both `QLength()` and `poll()`. That account was
tested and is **false on this host**: a round trip transfers such events into
Xlib's own queue, where `QLength()` sees them perfectly well.

The real defect is an ordering error, and it is worse because it needs no
transport subtlety at all:

1. `src/Events.cpp:195` tests `QLength(display())`. The queue is empty; the
   branch is not taken.
2. `src/Events.cpp:201` calls `XFlush()`. On this libX11 the flush path polls
   the transport — the disassembly shows `_XFlush` reaching
   `xcb_poll_for_event` / `xcb_poll_for_queued_event` — and it **moves the
   pending event into `dpy->qlen` while draining the socket.**
3. The code does not re-test `QLength()`.
4. `src/Events.cpp:205` calls `poll()` with `timeout = -1` whenever no focus
   timer is armed. The socket is now empty. **Nothing will ever wake it.**

Measured directly, replaying exactly those lines:

```
wm2 line 195  -> QLength=0   (branch NOT taken)
              -> fd readable=1
wm2 line 201  -> XFlush() called
wm2 line 205  -> QLength=1, fd readable=0
*** WEDGE CONFIRMED ***
```

The window manager sleeps indefinitely on an event it is already holding.

**This explains every reading the three measurement rounds produced**, which is
the strongest available check that it is the right mechanism and not merely a
real one: all five round-3 backtraces named `poll(nfds=2, timeout=-1)` at
`src/Events.cpp:205`, because that is precisely where it wedges; the round-4
control clients never framed even at the hard 8000 ms deadline, because nothing
can wake that poll; the round-4 intervention clients framed in 20–45 ms, because
any delivered event makes the socket readable, `poll()` returns, and the queued
backlog drains oldest-first; `recvq` read 0 in all 40 bundles, because `XFlush()`
had drained the socket; and the healthy calibration bundle showed the same frame
as the trips, because an idle window manager is legitimately in that same poll —
which is exactly why no backtrace could ever have separated the two.

**What this round does not claim.** It does not claim the release gate is now
reliable. That is a rate, and this round measures none.
</objective>

Replace the body of `WindowManager::nextEvent()` with the canonical shape. The
four invariants below are the specification; the code is whatever satisfies them
in this tree's idiom.

1. **Exactly one `XPending()` pump before every blocking `poll()`.** `XPending()`
   is `XEventsQueued(QueuedAfterFlush)`: it returns `dpy->qlen` when non-zero
   and otherwise flushes output and performs the non-blocking transport read. It
   therefore IS both the predicate and the flush, which is what removes the
   window the old code left between them.
2. **No Xlib call between a zero result from that pump and the `poll()`.** The
   only call permitted there is `computePollTimeout()`, which reads local state
   and cannot move an event between queues. Adding any Xlib call back into that
   gap reintroduces the defect in a new spelling.
3. **No `XNextEvent()` based solely on fd readability.** On a readable X
   descriptor, `continue` to the top and let `XPending()` decide. An ordinary
   event becomes pending and is returned; a protocol error is delivered to the
   error handler without waiting for a later event.
4. **The exit flag is checked independently of X queue depth.** Check it at the
   top of the loop, so a sustained event stream cannot starve shutdown, and
   again after the pump, since a signal can arrive while the flush is in
   progress.

Delete the standalone `XFlush()`. Keeping it after `XPending()` would move a
later-arriving event into the queue between the predicate and the `poll()` —
the identical race, relocated. This is the one edit in the task with no
discretion attached to it.

Handle the error revents explicitly. `POLLERR`, `POLLHUP` and `POLLNVAL` are
delivered by the kernel regardless of what `.events` requested, and the old code
tested only `POLLIN` — so an errored descriptor matched no branch, fell out of
the chain, and re-polled immediately at full CPU. Note in a comment that
`XFlush()` did not rescue this: with an empty output buffer the flush issues no
syscall, so Xlib never learned the connection was gone.

Give `m_signalled` a consumer. Its two writers are the signal handler
(`src/Manager.cpp:427`) and the menu's Exit item (`src/Buttons.cpp:591`); it has
no reader anywhere in the tree, which is why menu Exit currently sets a flag and
returns to the menu. Read it in the loop. Additionally have the menu path write
the self-pipe, so Exit wakes a blocked `poll()` the same way a signal does
rather than waiting for unrelated X traffic. Do not move any work INTO the
signal handler; it stays a flag write plus a pipe write.

Set `.revents = 0` before each `poll()` rather than relying on the previous
iteration's contents.

Keep the diagnostics in this tree's voice: the `wm2: ` prefix, one line, no
window ids or titles.
