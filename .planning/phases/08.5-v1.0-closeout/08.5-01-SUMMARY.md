## The finding that changed Task 1's shape

The plan called for an EWMH-first title read on the reasoning that
`_NET_WM_NAME` is UTF-8 and `WM_NAME` is not. What the code actually showed was
worse than that framing suggested: **nothing in the window manager read
`_NET_WM_NAME` off a client at all.** `Atoms::net_wmName` was interned and used
in exactly one place — naming the WM's own check window (`src/Manager.cpp:753`).

And `getProperty()` requested type `XA_STRING` unconditionally, so reaching for
the EWMH property through it would not have failed loudly. It would have returned
**empty through a silent type mismatch** — a config key that parses, matches
nothing, and reports nothing. That is the precise failure class the verifier
found four instances of in `docs/RELEASE-NOTES.md` at the end of Phase 8.

So the type became a parameter (defaulted, so all other call sites are
untouched), and the fallback is selected on the value being *empty* rather than
on a status, because a client may publish the property empty and an empty title
is exactly as useful as an absent one.

`eventProperty()` re-reads through the full precedence on **both** properties
rather than taking the event's own. A client that publishes both and then touches
the legacy one must not thereby replace the UTF-8 title it is still advertising;
a client that deletes `WM_NAME` while keeping `_NET_WM_NAME` must not end up
untitled. A naive `m_name = getProperty(a)` gets those wrong in opposite
directions.

## The key rename

`rule-match-name` compared the WM_CLASS instance name while its name said
WM_NAME. That confusion is not hypothetical — it is what put "matches the window
title" into the shipped release notes, where the phase verifier found it.

| Before | After | Compares |
|---|---|---|
| `rule-match-class` | `rule-match-class` | both WM_CLASS fields (the forgiving one) |
| `rule-match-name` | `rule-match-instance` | the WM_CLASS instance name |
| — | `rule-match-title` | the window title |

**No alias**, per D-8.5-01. v1.0 has not shipped, so nothing is owed to the old
spelling, and an alias for a key with no users outside this machine is permanent
surface bought for nothing. The cost is one line wide and visible: an existing
config gets the parser's unknown-key warning, and the action line after it is
then an orphan that warns separately — so the whole group contributes nothing
rather than half of it silently applying. Pinned by its own case.

The release notes carry a migration note for anyone who used the old key.

## The map-time semantic (D-8.5-03)

A title rule matches the title as it stands **when the window is mapped**. The
WM does not re-fold when a title later changes, and that is a choice with a
reason: re-applying a rule's position and size on rename would make a window jump
every time a document is saved under a new name or a browser tab is switched.

Stated in three places, as the plan required — the requirement text, the release
notes (in plain language, with the reason), and at the fold in `src/Client.cpp` —
and **pinned by a test that reddens if a re-fold is added**. Re-fold is on the
v1.1 backlog.

Every mutation run in **both** `build/debug` and `build/asan`. Each killed the

| # | Mutation | Result |
|---|---|---|

| M2 | title read EWMH-only, no fallback | kills the 3 legacy cases, including item 11's two |
| M3 | drop `hasMatchTitle` from the no-criteria guard | 4 `[rules]` failures |

| M5 | leave `facts.title` empty | kills the 3 matching `[wm_rules]` cases |
| M6 | **add** a re-fold on the title-change path | kills exactly the D-8.5-03 case |

M3 is the one worth keeping in mind: `ruleMatches()` discards a rule with no
criteria, and that guard enumerates the criteria explicitly. A criterion added to
the matcher but forgotten in the guard produces a rule that is thrown away before
it is ever compared — indistinguishable, from outside, from a rule that did not
match, and invisible to every positive test.

## Two harness defects found in my own tests

Both are the anti-patterns this phase keeps meeting, and both were caught by
running the checks the plan mandated rather than by inspection.

**1. The UTF-8 case passed vacuously.** Both its titles went through
`_NET_WM_NAME`, which the unfixed WM ignores entirely, so both tabs came back at
the same default-label length and every relative assertion held trivially. Fixed
with an untitled baseline and a growth `REQUIRE`.

**2. The D-8.5-03 case's vacuity guard did not guard.** It asserted
`longest > 0` over the frame's children — trivially true. Its two titles were
also the same length ("Drafts - Mail" / "Inbox - Mail"), so the tab could not
have moved even if the guard had been real. **Measured: deleting the retitle step
entirely left the case green.** Three things were wrong and all three had to be
fixed:

- the guard now measures the tab before and after and requires growth;
- the helper excludes the client window, which is reparented into the frame and
  is taller than the tab on any realistic test window — a naive "tallest child"
  reads the client and never changes;
- the window is 460 px rather than 220 px, because `fixTabHeight()` bounds the
  tab by the window it decorates: at 220 px the two titles gave 86 → 113, a real
  difference but a thin margin. At 460 px it is 86 → 325.

Verified after the fixes: retitle removed → 86 → 86, case RED.

## A defect found on the way, deferred rather than folded in

**Deferred item 18: a title in a script the tab font does not cover renders a
correctly-sized, blank tab.**

Found while writing the UTF-8 case, which first used CJK. Measured on this host,
35-character titles, tall window:

| Title | Tab length | Label ink |
|---|---|---|
| ASCII | 325 px | 611 px |
| Cyrillic (2-byte UTF-8) | ~325 px | > 0 |
| **CJK (3-byte UTF-8)** | **397 px** | **0 px** |

The string was measured, the tab grew to fit it, and not one pixel was drawn.
`Noto Serif CJK` **is installed** — this is missing *fallback*, not missing
fonts. `Border` resolves one face through fontconfig and draws the whole label
with it, and Xft draws nothing for a codepoint that face lacks. `src/Buttons.cpp`
has the identical single-face assumption for the menu.

This is a real gap in VISL-03's promise ("titles containing non-ASCII characters
display correctly"), which holds inside the resolved face's coverage and fails
silently outside it. It is deferred rather than fixed here because this plan's
subject is *which property the title comes from* and this is *how the label is
rendered* — Phase 4's machinery, and a real piece of work (per-run font selection
via `FcFontSort`, plus the same for the menu). A cheaper partial option is costed
in the deferred-items entry.

**It was caught by the ink assertion.** Every length-based assertion passed
happily on a blank label — which is the same lesson as the harness defects above,
arriving from a different direction.
