# Phase 08.5 Plan 11: Close the event loop's readiness-ordering defect Summary

This summary was written on 2026-09-05, after execution, from the plan's committed commits and evidence directory.

**The event loop's defect is an ordering error, not the previously-hypothesised libxcb transport-visibility problem: `XFlush()` moved a pending event into Xlib's own queue and drained the socket AFTER the queue-length predicate had already answered "nothing pending," so `poll()` blocked on an event the process already held. The earlier account was tested and found false on this host; a forty-line probe reproduced the defect deterministically in under a second, after three prior measurement rounds (08.5-06, -09, -10) spent themselves on statistical attribution without naming a mechanism.**

This plan makes no claim about the release gate's reliability going forward: that would be a rate, and this round measured none. Every claim below is a deterministic reproduction (the committed probe, or a Catch2 case that fails at a pinned commit and passes at another) or a source-level read of `src/Events.cpp` as it stood at the pinned round base.

## What was built

- **Task 1** pinned `ROUND_BASE` (`7de1bdc4aa6328571f3be999796b75eb7ae5d8a4`) and the pre-refactor `ctest -N` case list (316 cases), then extracted the loop's two decisions — the pre-poll pump and the post-poll action — out of `WindowManager::nextEvent()` into a new header-only `include/EventPump.h`, faithfully preserving both defects (the pump still flushed-then-reported-zero; the post-poll decision still delivered on bare `POLLIN`). `test_eventloop` was bound to the Xvfb fixture with the same three CMake properties (`ENVIRONMENT`, `FIXTURES_REQUIRED`, `RESOURCE_LOCK`) `test_client` carries, since it previously ran with no `DISPLAY` at all. Pinned at `e21be61` (`PLAN_11_T1`).
- **Task 2** added four deterministic Catch2 cases to `tests/test_eventloop.cpp`, each driving a symbol declared in `include/EventPump.h`: `pump-reports-what-is-available`, `pump-reports-zero-when-idle`, `readable-is-not-deliverable`, and `exit-flag-stops-the-loop`. Three failed at `PLAN_11_T1` for exactly the three defects named in the objective; the fourth (`pump-reports-zero-when-idle`) passed there and stayed passing, guarding against a stub fix. The failing run is captured in `red-before-fix.log`: exit code 8, three named failures, out of 11 cases selected by the `eventloop` label (9 real cases plus `start_xvfb`/`stop_xvfb`).
- **Task 3** fixed all four: the pump became `XPending()` (removing the standalone `XFlush()` entirely, not reordering it); the post-poll decision now re-pumps instead of delivering on a readable X descriptor; `POLLERR`/`POLLHUP`/`POLLNVAL` on either descriptor now produce an explicit `wm2: `-prefixed stop instead of falling through to an unhandled branch that re-polled at full CPU; and `m_signalled` gained a consumer in the loop (checked before and after the pump) with the menu Exit path (`src/Buttons.cpp`) also writing the self-pipe. All four Task 2 cases passed and the full debug suite stayed at 320/320.
- **Task 4** captured the passing run to `green-after-fix.log` (100% tests passed, 0 failed, out of 320), wrote `evidence/gates/eventloop/README.md` recording the mechanism, the four measured readings, the correction of the superseded libxcb-stranding account, a consistency check against the three prior rounds' readings, the before/after table for all four cases, and a "What this does not establish" section. It pinned `PLAN-11-TIP.txt` (`97a0042`) as Task 3's code tip, and triaged five audited-but-unfixed defects into `.planning/WINDOWS.md` via `gsd-tools windows append`, raising `open_count` from 7 to 12.

## The mechanism, as the README states it

Replaying `src/Events.cpp` as it stood at `ROUND_BASE`:

1. `:195` tests `QLength(display())`. Empty; branch not taken.
2. `:201` calls `XFlush()`. On this libX11 the flush path polls the transport (`_XFlush` reaches `xcb_poll_for_event`/`xcb_poll_for_queued_event`) and moves the pending event into `dpy->qlen` while draining the socket.
3. The queue length is never re-tested.
4. `:205` calls `poll()` with `timeout = -1` whenever no focus timer is armed. The socket is empty; nothing will wake it.

Measured by the committed probe (`evidence/gates/eventloop/wedge-probe.c`, output in `wedge-probe.log`):

```
line 195  -> QLength=0   (branch NOT taken)
          -> fd readable=1
line 201  -> XFlush() called
line 205  -> QLength=1, fd readable=0     *** WEDGE ***
```

The README states this explicitly corrects the earlier account, which held that events were stranded invisibly in libxcb's transport queue: that account was tested and found false on this host. The consistency section labels the agreement with the three prior rounds' readings (round-3 backtraces all naming `poll(nfds=2, timeout=-1)`; round-4 controls never framing; round-4 interventions framing in 20-45 ms; `recvq=0` in all 40 bundles; the healthy calibration bundle looking identical to a trip) as a consistency check, not independent confirmation, and states plainly that this round neither re-opens nor amends the 08.5-10 round-3 `REFUTED` finding, and does not rule the open 08.5-10 Task 3 checkpoint.

## Deviations from Plan

### 1. The Task 1 PROPS gate was unsatisfiable as originally written — corrected in `efba0a2`

The first execution of Task 1's plan reported `PROPS-MISSING 7` even though the mandated `CMakeLists.txt` change had genuinely taken effect on every discovered case. Per commit `efba0a2`'s message, this was for two independent reasons, both verified rather than assumed:

1. Binding `test_eventloop` to the Xvfb fixture pulls `start_xvfb` and `stop_xvfb` into the `-L '^eventloop$'` selection. Neither carries any of the three properties the gate checked for, so the gate's unfiltered `all(...)` over the selection was false by construction regardless of what the target's own registration looked like. The fix excludes them by name.
2. `ctest --show-only=json-v1` does not export `RESOURCE_LOCK` at all on ctest 3.22.1 (the exported property set is `DEPENDS`, `ENVIRONMENT`, `FIXTURES_CLEANUP`, `FIXTURES_REQUIRED`, `FIXTURES_SETUP`, `LABELS`, `SKIP_RETURN_CODE`, `TIMEOUT`, `WORKING_DIRECTORY`) — confirmed against `test_client`, which provably carries the lock at `CMakeLists.txt:243` and still reports no such property when queried this way. That conjunct of the gate was therefore permanently false and the lock could never be verified by effect through this mechanism; it is checked from the CMake source text by a separate `awk`-bounded gate instead.

Both corrected gates were smoke-tested to pass against the post-fix tree (`PROPS-OK 9`, `LOCK-PRESENT`) before being committed — the check the original gate lacked, per the commit message: it had been smoke-tested only for its ability to report failure, never for its ability to report success, which is the same class of defect the three prior review rounds are recorded as having found repeatedly in this plan during earlier drafting. The commit changes only `08.5-11-PLAN.md` (the gate text itself); no production or test code changed as part of this correction. `08.5-12` was checked for the same pattern per the commit message and does not carry it.

## Findings

- **The exit code recorded for the RED run is 8**, with three named failures out of 11 selected tests (9 real `eventloop`-labelled cases plus the `start_xvfb`/`stop_xvfb` fixture tests); ten consecutive runs at that commit produced ten identical exit codes of 8, per the README.
- **The GREEN run is 320/320 (100%) passing**, confirmed directly against `green-after-fix.log`; ten consecutive runs of the `eventloop` label after the fix produced ten identical exit codes of 0, per the README.
- **Menu Exit was verified against the built binary, not only the token gate**: per the README and the Task 3 commit message, driving the root menu over XTEST and selecting Exit terminated the window manager with status 0 — something that could not have worked at `ROUND_BASE`, where `m_signalled` had one definition, one declaration, two writes, and no read anywhere in the tree.
- **The full suite was not uniformly green run to run, on either side of the fix, recorded as counts and not a rate**: at `ROUND_BASE`, two full-suite runs gave one clean run and one with four failures (a reparent-deadline timeout and three others), each of which passed when re-run alone; after the fix, three full-suite runs gave two clean runs and one with a single failure (a menu-background-colour case whose sampled menu was unpainted), which then passed ten out of ten times when run alone. The README states explicitly that whether this round changed that behavior is the question it does not answer.
- **Five defects were audited but deliberately not fixed this round**, each recorded in `.planning/WINDOWS.md` (entries 8-12, added via `gsd-tools windows append`) with file:line and a concrete failing interleaving: modal `XMaskEvent` loops that cannot be interrupted by the self-pipe (`src/Buttons.cpp:156`, `:530`, `src/Border.cpp:1495`, `src/Client.cpp:1592`, `:1705`, `:2228`) — destination 08.5-13; the root menu discarding foreign `Expose` events instead of dispatching them (`src/Buttons.cpp:530`) — destination 08.5-13; an Enter-coalescing/ignored-Leave focus livelock (`src/Events.cpp:551`) — destination 08.5-13; `StructureNotifyMask` truncated out of the pointer-grab mask by a 16-bit intermediate (`src/Buttons.cpp:16`, `src/Border.cpp:1458`) — destination 08.5-13; and `m_currentTime` declared `int` rather than `Time` (`include/Manager.h:215`) — destination 08.5-12. `open_count` in `.planning/WINDOWS.md` rose from 7 to 12 as a result, which per that file's own header blocks `/gsd-ship` under `windows_enforce` until addressed or waived.
- **This plan did not rule the open 08.5-10 Task 3 checkpoint** and wrote no outcome word (`Verdict`, `Attribution outcome`, `Terminal disposition`, `08.5-07 disposition`) into any file it touched, per its own prohibition and the gate that checks for those exact strings.
