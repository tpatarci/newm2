## Summary

Phase 8.5 does three things: it completes RULES-01 (`rule-match-title` plus an
EWMH-first title read), it restyles the frame (silver palette, Ubuntu font, a
1 px active-only bevel, `destroy-window-delay` 1500 -> 400), and it closes out
release evidence (TightVNC and nxagent captures, two validation scripts).

The **rules half is the strongest work in the diff**. `getWindowTitle()` gets
the precedence right in both directions, `ruleMatches()`'s criterion-free guard

The **appearance half is where the defects are**, and they cluster on one new
function: `WindowManager::allocateShadeOf()`. It has a fatal path on precisely
the condition its own comment says must never be fatal, it uses pixel `0` as a

values (`#F2F4F6 / #898C8F`) that the shipped blend does not produce — the test
added alongside it states the correct ones (`#F2F3F3 / #898A8B`, verified by
running the case).

`docs/RELEASE-NOTES.md` was edited in this diff, and the section it did *not*
edit now contradicts `COMPILED_CODE_BEHAVIOR_CHECKLIST.md` in the same commit

For a project whose stated standard is that a false promise in a shipped

### CR-02: Predictable world-writable temp file in `stress-exerciser.sh` (CWE-59 / CWE-377)

**File:** `scripts/stress-exerciser.sh:61,64,108,115`
**Issue:** the window manager's stdout/stderr is redirected to the fixed path
`/tmp/wm2-stress-wm.log`:

```bash
DISPLAY="$DISPLAY_NUM" "$WM" > /tmp/wm2-stress-wm.log 2>&1 &
```

`>` follows symlinks and `set -C` is not in effect. On a shared host any other
local user can pre-create `/tmp/wm2-stress-wm.log` as a symlink to a file the
script's operator owns (`~/.bashrc`, `~/.ssh/authorized_keys`, a source file)
and that file is truncated and then overwritten with WM output the attacker also
partly controls, since X protocol error messages echo client-supplied values.
Two concurrent runs also clobber each other, and `grep -c` at line 115 then
counts another run's errors.

**Fix:**

```bash
LOGDIR="$(mktemp -d "${TMPDIR:-/tmp}/wm2-stress-XXXXXX")"
WM_LOG="$LOGDIR/wm.log"
# ... and in cleanup():
#   rm -rf "$LOGDIR"
DISPLAY="$DISPLAY_NUM" "$WM" > "$WM_LOG" 2>&1 &
```

then replace the three remaining literal `/tmp/wm2-stress-wm.log` uses with
`"$WM_LOG"`.

### CR-03: `allocateShadeOf()` calls `fatal()` on the exact condition it documents as non-fatal

**File:** `src/Manager.cpp:720-728`, and its own contradicting comment at
`src/Manager.cpp:752-755`
**Issue:**

```cpp
if (!XAllocNamedColor(display(), DefaultColormap(display(), m_screenNumber),
                      name, &nearest, &ideal)) {
    char error[100];
    std::snprintf(error, sizeof error, "couldn't load %s colour", desc);
    fatal(error);            // <-- exits the window manager
}
```

`XAllocNamedColor` does **both** a name lookup and a colormap allocation. It
returns zero on a full read/write colormap, not only on an unparseable name. So
on an 8-bit PseudoColor display with a saturated colormap, the *first* branch of
this function kills the window manager at startup with
`wm2: couldn't load bevel highlight colour` — while the function's own comment
seventeen lines below says the opposite:

> "A failed allocation here is NOT fatal, unlike the named-colour path above.
> This is decoration: on a display whose colormap is full, the correct outcome
> is a frame without bevels, not a window manager that refuses to start."

`include/Border.h:183-184` makes the same promise ("Either GC may be null when
the colormap is full ... no bevel is the correct degradation, not a fatal
error"), and `src/Border.cpp:84-86` repeats it. All three are wrong about what
the code does. This is reachable on TightVNC 1.3.10 and other low-depth remote
servers, which is the deployment class this project exists for.

The bug also allocates a colormap cell the function never uses: only `ideal`
(the exact parsed RGB, which needs no allocation) is read; `nearest` is discarded.

**Fix:** use a lookup that does not allocate, and never exit from this path.
The caller already treats failure as "no bevel":

```cpp
unsigned long WindowManager::allocateShadeOf(const char *name, double fraction,
                                             const char *desc, bool *ok)
{
    Colormap cmap = DefaultColormap(display(), m_screenNumber);
    XColor ideal;
    if (!XParseColor(display(), cmap, name, &ideal)) {
        std::fprintf(stderr, "wm2: warning: could not parse the %s base colour "
                             "'%s', frames will be drawn without bevels\n",
                     desc, name);
        if (ok) *ok = false;
        return 0;
    }
    // ... blend as today ...
    if (!XAllocColor(display(), cmap, &shade)) {
        std::fprintf(stderr, "wm2: warning: could not allocate the %s shade, "
                             "frames will be drawn without bevels\n", desc);
        if (ok) *ok = false;
        return 0;
    }
    if (ok) *ok = true;
    return shade.pixel;
}
```

(The `ok` out-parameter also fixes WR-01 below; see that finding.)

### WR-01: Pixel `0` used as a failure sentinel, but `0` is a legal allocated pixel

**File:** `src/Border.cpp:79-104`, `src/Manager.cpp:756-758`
**Issue:** `allocateShadeOf()` returns `shade.pixel` on success and `0` on
allocation failure; the caller encodes that convention explicitly:

```cpp
// A zero pixel means the allocation failed and the GC stays null ...
if (lightPixel != 0) { ... }
if (shadowPixel != 0) { ... }
```

On a TrueColor visual, pixel `0` is pure black and is what `XAllocColor` returns
for RGB(0,0,0). A user who sets a dark palette — `tab-background = black`, or
anything that blends to black at `-0.315` — gets a *successful* allocation that
the caller silently discards as a failure. No warning is printed, because the
warning lives on the real failure path. The result is a bevel that is
half-drawn (highlight only) for dark themes, with no diagnostic.

This is the same class of defect the codebase already flagged in
`include/Rules.h:66-75` for `RuleTriState`: a sentinel that collides with a
legal value.

**Fix:** return success out-of-band, per the CR-03 snippet:

```cpp
bool lightOk = false, shadowOk = false;
const unsigned long lightPixel  =
    windowManager()->allocateShadeOf(tabBg,  0.76,  "bevel highlight", &lightOk);
const unsigned long shadowPixel =
    windowManager()->allocateShadeOf(tabBg, -0.315, "bevel shadow",    &shadowOk);
if (lightOk)  { /* build m_bevelLightGC  */ }
if (shadowOk) { /* build m_bevelShadowGC */ }
```

### WR-02: Bevel colours leak two colormap cells per Border-statics cycle

**File:** `src/Border.cpp:73-105` and `src/Border.cpp:135-153`,
`src/Manager.cpp:717-761`
**Issue:** `Border::~Border()` deliberately resets `m_staticsInitialised = false`
when the last Border dies (`src/Border.cpp:153`), so the next window re-runs the
whole static-initialisation block — including the two `allocateShadeOf()` calls.
Each call performs an `XAllocNamedColor` (one cell, immediately discarded — only
`ideal` is used) plus an `XAllocColor` (one cell, kept). `XFreeColors` is never
called anywhere for these. The teardown at `src/Border.cpp:139-140` releases the
GCs but not the pixels.

On a TrueColor/DirectColor visual this is harmless. On PseudoColor — an 8-bit
VNC or XRDP session, which the release notes explicitly discuss at
`docs/RELEASE-NOTES.md:80-83` — a session that repeatedly reaches zero managed
windows and then opens another will exhaust the default colormap, at which point
CR-03 turns the leak into a startup abort. Four cells per cycle, two of them
never used.

The pre-existing `allocateColour()` has the same shape, so this is aggravated
rather than introduced — but the new code doubles the per-cycle cost and adds
the two wasted `XAllocNamedColor` cells.

**Fix:** remember the pixels alongside the GCs and free them in the same
`--m_borderCount == 0` block:

```cpp
static unsigned long m_bevelLightPixel;   // 0 == not allocated
static unsigned long m_bevelShadowPixel;
// ... in ~Border(), inside the m_borderCount == 0 block:
Colormap cmap = DefaultColormap(display(), DefaultScreen(display()));
unsigned long px[2]; int n = 0;
if (m_bevelLightGC)  px[n++] = m_bevelLightPixel;
if (m_bevelShadowGC) px[n++] = m_bevelShadowPixel;
if (n) XFreeColors(display(), cmap, px, n, 0);
```

and drop the `XAllocNamedColor` in favour of `XParseColor` (CR-03) so the
discarded cell is never allocated at all.

### WR-07: The tab bevel is unreachable on the font ladder's last rung, while the button bevel is not

**File:** `src/Border.cpp:553-579`, `src/Border.cpp:1308-1311`
**Issue:** `drawBevel()` is called from exactly one place — inside
`drawLabel()`, at line 579, *after* two early returns:

```cpp
void Border::drawLabel(bool active)
{
    if (!hasTabFont()) return;        // rung 4: never reaches drawBevel()
    if (m_label.empty()) return;      // ditto
    ...
    drawBevel(active);                // line 579
```

### WR-08: Tab bevel highlight and shadow sit at different insets from the shape edge

**File:** `src/Border.cpp:496-520` vs `src/Border.cpp:925-926`
**Issue:** the tab's clip (drawable interior) for the main column is

```cpp
appendRect(1, m_tabWidth - TAB_TOP_HEIGHT + 1, m_tabWidth, ...);  // x = 1 .. m_tabWidth
```

so the interior spans x=1 through x=m_tabWidth inclusive. `drawBevel()` puts the
highlight on x=1 — the leftmost interior pixel, correct — but the shadow on

```cpp
const int right  = m_tabWidth - 1;
shadow[0].x1 = right; shadow[0].y1 = m_tabWidth;
shadow[0].x2 = right; shadow[0].y2 = bottom;
```

That is one pixel *inside* the right edge, leaving a body-coloured pixel between
the shadow and the black outline. The bevel is asymmetric: flush on the left,
inset on the right. The `[wm_bevel]` test only asserts `> 0` shadow pixels, so it
cannot catch this.

**Fix:**

```cpp
const int right = m_tabWidth;   // the rightmost pixel of the clip interior
```

and re-check the same value against the top-band and right-strut clip rects at
`src/Border.cpp:920-924` before committing — the assertion worth adding is an
absolute one (the shadow column index), not a count.

### WR-09: Full Xft tab repaint added to every activation, including no-op re-activation

**File:** `src/Border.cpp:1299-1312`, reached from `src/Client.cpp:304-306`
**Issue:** `Border::decorate()` previously did one thing —
`setFrameVisibility()`. It now also runs `drawLabel(active)`, which is an
`XftDrawRect` over the whole tab plus an `XftDrawStringUtf8`. There is no dirty
check on `active`, and `Client::activate()` has an explicit already-active fast
path that still pays the cost:

```cpp
if (isActive()) {
    decorate(true);     // full tab re-render for a state that did not change
    return;
}
```

Under the default focus-follows-pointer policy, every focus transition now
pushes two full tab repaints (deactivate the old window, activate the new) over
the wire, and a re-activation of the already-active window pushes one for
nothing. On the VNC/XRDP targets this project is built for, a redundant Xft
repaint is visible as flicker, not merely as cost.

(Raw throughput is out of v1 review scope; this is reported for the redundant
repaint on an unchanged state and the flicker it causes, not for the algorithm.)

**Fix:** remember the last painted state and skip the repaint when it has not
changed:

```cpp
// in Border: bool m_lastDrawnActive = false; bool m_everDrawn = false;
void Border::decorate(bool active, int w, int h)
{
    setFrameVisibility(active, w, h);
    if (isTransient()) return;
    if (m_everDrawn && m_lastDrawnActive == active) return;
    m_everDrawn = true;
    m_lastDrawnActive = active;
    drawLabel(active);
    drawBevel(active);
    drawButtonBevel(active);
}
```

`rename()` and `Border::expose()` must clear `m_everDrawn` (or call `drawLabel()`
directly) so a title change and an exposure still repaint.

entire output is a judgement call about a trend, a zero-iteration run must not
be indistinguishable from a passing one.

**Fix:**

```bash
case "$CYCLES$WINDOWS" in
    *[!0-9]*|'') echo "wm2: cycles and windows must be positive integers" >&2; exit 2 ;;
esac
[ "$CYCLES" -ge 1 ] && [ "$WINDOWS" -ge 1 ] || {
    echo "wm2: cycles and windows must be >= 1" >&2; exit 2; }
```

and assert at the end that the loop actually ran (`[ "$c" = "$CYCLES" ]`).

### WR-12: The exerciser's X-error column is cumulative but presented per-cycle

**File:** `scripts/stress-exerciser.sh:71-73,112-118`
**Issue:** the table header declares a per-cycle `X-errors` column, but line 115
greps the *entire* log every cycle:

```bash
ERRS=$(grep -c "X protocol error\|BadWindow\|..." /tmp/wm2-stress-wm.log ...)
```

so the number is a running total. A reader watching for "errors started at cycle
7" sees a monotonically rising count with no way to attribute it. The adjacent
`clients` column is a hardcoded `"0"` on every row (lines 73 and 117) and
conveys nothing.

**Fix:** track the previous total and print the delta; drop or populate the
`clients` column:

```bash
PREV_ERRS=0
# ...
TOTAL_ERRS=$(grep -c "..." "$WM_LOG" 2>/dev/null) || true
TOTAL_ERRS="${TOTAL_ERRS:-0}"
ERRS=$((TOTAL_ERRS - PREV_ERRS)); PREV_ERRS=$TOTAL_ERRS
```

### WR-13: Titles are truncated at 400 bytes before rule matching, so an exact title rule cannot match a long title

**File:** `src/Client.cpp:873-893` (`getProperty`), consumed by
`src/Client.cpp:1114` (`facts.title = m_name`)
**Issue:** `getProperty()` reads through
`getProperty_aux(display(), m_window, a, type, 8, 100L, &p)`. `XGetWindowProperty`
counts `long_length` in 32-bit units, so `100L` caps the read at **400 bytes**.
That was harmless while the title only fed the tab label (which truncates
anyway). Now `rule-match-title` compares against it, and
`rule-match-mode = exact` against a title longer than 400 bytes can never match —
silently, with no warning, which is the exact failure class this phase set out to
remove (`include/Rules.h:90-98`: "a control that looks available and silently
does nothing").

The config side accepts criterion values up to 256 characters
(`src/Config.cpp:126-129`), so the mismatch is not obvious from either end.

**Fix:** either raise the read for title properties, or record the truncation.
Minimum viable:

```cpp
// 100L is 400 bytes for a format-8 property. Titles longer than that are
// truncated, which rule-match-title with mode=exact cannot match. Raised to
// cover the config value limit (256 chars) with margin.
const int n = getProperty_aux(display(), m_window, a, type, 8, 1024L, &p);
```

and add a `[rules]` case that pins the behaviour at the boundary either way.
