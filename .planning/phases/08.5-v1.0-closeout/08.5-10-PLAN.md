Attribute the post-readiness reparent wedge to a named failing path by
**intervening** on it, with a control arm — or end the attribution effort at a

Purpose. Plan 08.5-09 measured the leading hypothesis and refuted it: five
readable hang-time backtraces from three distinct window-manager processes all
named `WindowManager::nextEvent` at `src/Events.cpp:205`, inside the event
loop's own `poll(nfds=2, timeout=-1)`, and none named the timestamp path. The
operator ruled `REFUTED` with the `08.5-07` disposition `RE-PLAN`. That ruling,
the figures behind it and the three held plans are all untouched by this round.

What that round could not do was attribute, and the reason is precise rather
than rhetorical: **the healthy-window-manager calibration bundle shows the same
frame.** An idle window manager with nothing to do and a window manager that has
failed to reparent a client for 500 ms are, at the level a backtrace reads, in
the same place. A backtrace can therefore refute a mechanism and can never, by
itself, distinguish "idle because there is nothing to do" from "idle while
holding work it cannot see". Adding a sixth passive channel would not change
that. This round changes the *kind* of evidence instead.

The named failing path, and why it is a reading rather than a guess.
`WindowManager::nextEvent()` decides whether work is waiting by consulting
Xlib's own queue length at `src/Events.cpp:195`, and if that reads zero it
flushes output and blocks in `poll()` on the connection descriptor at
`src/Events.cpp:205`. The call that transfers events the transport has *already
read off the socket* into that queue appears nowhere in this tree — a grep for
it across `src/` and `include/` returns nothing, and the flush before the poll
only writes. On this host `libX11.so.6` is linked against `libxcb.so.1`, which
is checkable and was checked, so the transport genuinely maintains a queue of
its own. Every framing operation the window manager performs issues replies —
window attributes, properties, sync — and a read that satisfies one reply can
carry further events into the transport's queue in the same burst. Those events
are off the socket, so `poll()` will never report the descriptor readable for
them; and they are not in Xlib's queue, so the length check reads zero. The
window manager blocks with no deadline armed while holding undelivered work.

That account is not offered as a conclusion. It is offered because it is the
only candidate this phase has that predicts, without adjustment, every reading
the previous round actually recorded: the blocked poll with `timeout=-1` in all
five bundles; the identical frame in the healthy control; and — most usefully —
the `BadWindow` cascade the operator recorded as a lead and explicitly refused
to attribute. Under this account the cascade is a downstream signature rather
than a cause: the sampler destroys the unframed client when the deadline
expires, that destruction puts new bytes on the window manager's connection, the
poll finally returns, the backlog drains oldest-first, and the window manager
frames a window that no longer exists — which is exactly the observed sequence
of create, reparent, map and save-set requests all failing on one window id. The
cascade appearing in three of five bundles and not five of five is consistent
with that too, since a bundle's stderr is a snapshot taken at the trip and only
shows cascades that earlier iterations already produced.

**None of that is evidence yet.** A story that fits the readings is what the last
two rounds each had before they measured. This round exists to make the account
break if it is wrong.

The experiment. At a trip — a client unframed 500 ms into a poll whose hard
deadline is 8000 ms — the instrument captures the bundle exactly as before, and
then, on alternating trips, delivers to the window manager **one event its own
handler treats as a no-op**: a property change on the root window. The root
event mask carries the property bit (`src/Manager.cpp:605`, the last term of the
mask assignment spanning `src/Manager.cpp:603-605`) so delivery is
certain, and `eventProperty()` (`src/Events.cpp:535`) resolves the root window
to no managed client, so the handler returns having done nothing. The event adds
bytes to the connection and adds no work. If the window manager is holding an
undelivered map request, the poll returns, the backlog drains, and the stalled
client frames within milliseconds. If the map request never reached it, the
no-op is all that happens and the client stays unframed. The other half of the
trips get the identical capture and no event, which is what makes the debugger
attach — which interrupts a blocked poll and is therefore a real rival cause —
common to both arms instead of confounded with the intervention.

An intervention with a control arm is a different class of evidence from the
rate comparison this phase already had to correct once. It is also narrower, and
the record says so: it can name the failing path and it cannot produce a rate.

Termination, which is the part that is not optional. An accepted adversarial
finding on this phase reads: *"You have not demonstrated a repetitive technical
loop. You have demonstrated a decision process without a terminal rule."* Two
rounds before this one ended without ending. Task 3 carries a **precommitted
terminal rule** written here before the round runs, enumerating every outcome.
An attribution sends the phase to a fix plan. **Every other outcome — an inert
intervention, arms that do not separate, too few trips, no trips at all, an
unreadable instrument — lands on the same fixed three-item menu of terminal
dispositions, and "measure again" is not on it.** The operator chooses which
ending; the menu is not theirs to extend at the checkpoint, because a menu that
can grow at the checkpoint is the absence of a terminal rule wearing one.
