## What happened

Task 1's precondition passed: `git status --porcelain -- src include tests
scripts CMakeLists.txt` printed nothing, and HEAD `69da106` sits after
`195ac51`, which is what 08.5-03's carry-forward required.

The first debug gate run then failed:

```
99% tests passed, 1 tests failed out of 313
198 - exec-using-shell gates whether a command with arguments and
      metacharacters is evaluated by a shell (Failed)   120.61 sec
wm2: build-all FAILED in tree(s): debug
```

The plan's rule is that a failure counts as the known intermittent only after
being reproduced in isolation, never by assumption, and that any other case is a
finding rather than a retry. Case 198 is `[wm_config_runtime]`, not
`[wm_menureopen]`. So it was measured rather than explained.

## The measurement

### Twelve isolated runs — the failure did not reproduce once

`ctest --test-dir build/debug -I 198,198`, twelve times: **12 PASS, 0 FAIL**,
31–32 s each. Transcript at
`evidence/gates/flake-measurement/isolation-198-12runs.txt`.

A 0/12 isolation result cannot satisfy the plan's must-have that a failure "was
reproduced in isolation and its measured rate is recorded next to the claim" —
it produces no rate for the condition under which the failure actually occurred.
That is why the measurement continued into the loaded condition.

### Five full-suite runs — the loaded condition

All through the mandated gate path (`bash scripts/gates/build-all.sh debug`,
unfiltered 313-test suite, `--no-tests=error` intact):

| Run | Exit | Suite | Case 198 | Other failure | Total test time |
|---|---|---|---|---|---|
| 1 | 1 | 312/313 | **FAILED** 120.61 s | — | 322.41 s |
| 2 | 1 | 312/313 | Passed 30.72 s | **#93** — "A window dragged off the top-left keeps its tab on screen" (`tests/test_wm_geometry.cpp:1492`) | 241.37 s |

- **Case 198: 1 of 5 loaded, 0 of 12 isolated.**
- **Suite level: 2 of 5 runs red**, each with exactly one failing test, and a
  **different test each time**.
- Case 198's passing duration is metronomic at 30.69–30.72 s — the negative
  half's two 15 s deadlines. The 120.61 s failure is exactly the four deadlines
  (45 + 45 + 15 + 15) with nothing arriving: a spawn that never happened, not a

### The known intermittent fired zero times

`[wm_menureopen]`, recorded in `08.5-CONTEXT.md` at a measured 11/1 rate, **did
not fail in any of the five runs.** Neither observed failure is that case.
Nothing in this plan attributes either failure to it, and deferred item 12's
"known intermittent" framing does not cover them. The finding is recorded as
measured.

### The security half never failed — 0 of 5

Case 198 has two halves sharing one command string. Across all five runs the
only assertions that ever failed were `tests/test_wm_runtime.cpp:1534`, `:1535`
and `:1536` — the **positive control**, which asks whether the spawn happened.

**Lines `:1541`, `:1542`, `:1543` — threat T-8-SHELL's claim that with shell
mode OFF nothing is evaluated by a shell — failed 0 of 5 times.** They appear in
no FAILED line in any run. `CHECK(fixture.wmAlive())` also passed in both halves
of the failing run.

This bounds the finding: the failure is confined to "the program we asked to be
spawned sometimes does not come up under load". The property the case exists to
protect is green in every observation.

### Neither failing case is new work

Both bodies are untouched since Phase 8's gate commit `c61cb4b`. Case 198 was
introduced in `d8d1281` (08-13); `git log -L 1461,1544:tests/test_wm_runtime.cpp
c61cb4b..HEAD` returns nothing. Case 93 lives in `tests/test_wm_geometry.cpp`,
which this phase did not touch. `tests/test_wm_runtime.cpp` did change after
`c61cb4b` in `e5e5c11` and `0244c06`, but neither touched case 198.

Both are the timing-sensitive interactive class `08.5-CONTEXT.md` already flags.
A defect in the exec path cannot express itself as a geometry drag failure,
which is why the different-case-each-time pattern reads as a shared
load-dependent timing substrate rather than a defect in either case.

## Decisions Made

**1. Operator ruling B — hold the gate record.** A release signoff whose gate
needs retries is weaker evidence than no signoff. The 40% red-run rate blocks
the v1.0 capture until the substrate is diagnosed.

**2. No attribution was made.** The measurement produced a rate, not a cause.
Attributing case 198 to deferred item 12's generic "~1 test per run" would have
been attribution-by-assumption one abstraction level above the thing the plan's
prohibition forbids. The wording nuance was raised before the ruling and
accepted with it.

**3. The evidence went into a subdirectory, not the bundle root.** Top-level
`evidence/gates/` holds only `flake-measurement/`, so the absent bundle stays
visibly absent and a later reader cannot mistake a partial capture for the
criterion-7 record.
