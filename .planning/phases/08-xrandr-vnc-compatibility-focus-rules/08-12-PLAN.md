  <action>
Extend `tests/test_wm_state.cpp` with a group tagged `[wm_props]` covering the nine behaviours above.

Write each malformed property directly with a property-change call from the test's own connection, choosing the type, format and item count deliberately — that is the point of the group, so do not go through any convenience helper that would normalise them.

For the oversized-array case, write an array large enough to exceed the WM's bounded request length several times over and assert both that the WM survives and that it finishes within a deadline; a hang is as much a failure as a crash and only a deadline distinguishes them.

For the deleted-property case, delete the property after the window is managed and let the resulting change notification drive the re-read, rather than deleting it before mapping — the interesting path is the one that runs against an already-populated client.

For the strut cases, assert the resulting workarea is a valid rectangle with non-negative width and height that does not exceed the screen, rather than asserting one specific clamped value; the requirement is that the clamp holds, not that it produces a particular number.

Case 9 exists because individual malformed properties are often survivable while a sequence of them is not: run the whole battery against one window, then assert the WM still responds, still has a self-consistent client list, and still frames a newly mapped window correctly.

Any genuine defect these cases find is fixed in the corresponding reader in `src/Client.cpp` or `src/Manager.cpp` and recorded in the plan summary. Every reader must check the returned type, format and item count before trusting data and must free the returned buffer on every path — these are untrusted client inputs, and this group is the evidence for that claim.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| X client → WM (properties) | Every client-written property is untrusted input with attacker-chosen type, format, length and content |
| X client → WM (client messages) | Message format and data fields are attacker-chosen |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-8-PROP | Tampering | All `XGetWindowProperty` consumers in `Client` and `Manager` | high | mitigate | The malformed-property group exercises wrong type, wrong format, empty and oversized arrays, and deleted properties against every reader, under the sanitizer. Any reader that fails is fixed to check type, format and item count and to free on all paths. |
| T-8-STRUT | Denial of Service | Dock strut values feeding the workarea computation | high | mitigate | Cases 6 and 7 assert the workarea stays a valid non-negative rectangle bounded by the screen for oversized and out-of-range struts, so a hostile dock cannot make the workarea inverted or empty. |
| T-8-DOS | Denial of Service | Oversized property arrays | medium | mitigate | Case 4 asserts the read stays within the WM's bounded request length and completes within a deadline, so neither memory exhaustion nor a hang is possible from a large property. |
| T-8-MSG | Tampering | Client-message format and field validation | medium | mitigate | Cases 5, 7 and 8 of the message matrix assert that unsupported, wrong-format and misaddressed messages leave observable state byte-identical. |
| T-8-UAF | Elevation of Privilege | Teardown while fullscreen, where the frame is stripped and rebuilt | high | mitigate | Case 5 of the fullscreen group destroys a client mid-fullscreen under the sanitizer. |
| T-8-SC | Tampering | No package installs in this plan | low | accept | This plan adds no dependency of any ecosystem; nothing to audit. |
</threat_model>
