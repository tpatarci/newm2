    - Test 2: click-to-focus off — the pointer entering a window's frame eventually makes it the active window without any click, after the configured delays.
    - Test 3: auto-raise off — pointer entry never raises the window above a neighbour that overlaps it, and the WM's poll loop reports no armed deadline.

  <action>
Add the three gates at the exact points the research enumerated. Each gate reads its boolean from the config the `WindowManager` already holds; reach it through the existing `windowManager()->config()` accessor from `Client`, and directly from the member in `WindowManager`.

**click-to-focus.** `Client::eventEnter()` currently calls straight into the manager's focus-change consideration on every pointer entry. When the boolean is set, that call must not happen — focus then arrives only from the trailing activate at the end of `eventButton()`, which already exists and needs no change. Guard the call, do not delete it.

**auto-raise.** The gate belongs where the auto-raise deadline is armed inside the manager's focus-change consideration, not in the timer-expiry branches. When the boolean is clear, do not arm the deadline. The poll-timeout computation then correctly reports no active deadline and the loop blocks indefinitely, which is both the behaviour the user asked for and the checklist's no-idle-CPU-spin requirement. Do not add a substitute timer, and do not change the pointer-stopped deadline, which serves a different purpose.

**raise-on-focus.** This is the one boolean whose meaning is currently fused into another action: two sites activate a window and raise it as an inseparable pair. Split them at both sites — the activation always happens, the raise happens only when the boolean is set. The two sites are the manager-driven focus application in `Client::focusIfAppropriate()` and the focus-in event handler `Client::eventFocusIn()`. Both must be split identically or the two paths would disagree.

Cite the decisions in comments at each gate in the codebase's established form: the finding that these booleans had zero runtime consumers, and the decision to keep three booleans rather than introduce an enum.

Change no timer arithmetic and no state-machine structure. This plan decides *whether* the existing machinery runs, not *how* it runs.
  </action>
