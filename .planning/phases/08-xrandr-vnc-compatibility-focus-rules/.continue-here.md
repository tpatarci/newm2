## The menu rework (done by the orchestrator, not a subagent)

The operator rejected shipping a partly-working menu and asked for the
implementation to be reviewed and engineered properly. Two commits:

**`12f6de8`** — the WM was managing its OWN menu/submenu/WM-check windows as
clients (deferred item 7). Now created override-redirect. **The flag must be in
the `XCreateWindow` creation valuemask**: `CreateNotify` carries the
creation-time value, so `XChangeWindowAttributes` afterwards is too late —
measured, that version left all four windows in `_NET_CLIENT_LIST`. Also here:
`attemptGrab()` now takes `Time` not `int` (signed overflow past ~24.8 days of
server uptime silently voided every grab), and the drag geometry readout got its
own window instead of borrowing `m_menuWindow`.

**`fa33f2e`** — one grab, one loop for the whole interaction.
`openCategorySubmenu()` is DELETED. It used to ungrab, take a second grab with
`owner_events=False`, and run a nested loop that then owned every pointer event —
which is why the outer menu froze with no way back. Pointer is now read in ROOT
coordinates and hit-tested against rectangles `menu()` itself chose. The
highlight model updates on every motion even before the first `Expose` (a dropped
motion is never replayed).

New test `[wm_menuback]` covers mid-interaction back-travel, which
`[wm_menureopen]` does NOT (that one releases first). Both mutations redden it.
