Add window matching rules to the existing config file: a plain-data rule model, a hand-rolled matcher with exact and substring comparison, and a repeated-key-group parser that reuses the accumulator shape Phase 7 already proved. Parsing and matching only — applying the rules to real windows is plan 08-10.

Purpose: keeping the model and matcher X11-free means the whole of RULES-01 is unit-testable in milliseconds without a display, which is where the parser's edge cases actually get covered.
Output: `include/Rules.h`, `src/Rules.cpp`, the `rule-*` config keys, and `tests/test_rules.cpp`.
</objective>

  <action>
Create `include/Rules.h` following `include/AppEntry.h` exactly: `#pragma once`, standard-library includes only, no X11 include of any kind, scoped enumerations for closed vocabularies, defaulted members, and a header comment stating that the absence of an X11 dependency is deliberate so the rules tests stay display-free.

Define a match-mode enumeration with exactly two values, exact and substring. Define a window-type enumeration for the rule vocabulary with exactly four values — normal, dock, dialog and notification — mirroring the four the WM actually distinguishes; do not offer values that collapse into normal at runtime, because a user writing one would get a rule that silently never fires.

Define the rule structure with three optional criteria — class text, name text, and window type — each with an accompanying flag or optional-style marker recording whether the user set it, plus the per-rule match mode defaulting to substring. Alongside them, define the three shipping actions as tri-state values: unset, set-true and set-false for the no-decorate and skip-taskbar flags, and an unset-or-present pair of integers for position and another for size. Tri-state is required, not cosmetic: the later-wins fold cannot distinguish "this rule did not mention no-decorate" from "this rule turned no-decorate off" if the field is a plain boolean. Deliberately define no action that runs a command; the phase carries an explicit prohibition on introducing any shell-capable rule action.

Create `src/Rules.cpp` with two free functions. The first answers whether one rule matches a window described by its instance name, class name and type — all criteria the user set must match, using the rule's mode, with the class criterion tested against both the instance and the class name. A rule with no criteria set matches nothing.

The second folds an ordered list of rules against the same window description and returns a single resolved outcome: for each action, the value from the last matching rule that set it. This is what lets a user layer a broad rule plus a specific override.

Add a comment in the codebase's established form citing the decisions this implements: repeated key groups, all-criteria-must-match with exact and substring only, and later-wins-per-action ordering. Note explicitly in the header that the deliberately-excluded workspace action from the requirement is recorded in plan 08-10's amendment.

  <action>
Add a rules vector to `Config` beside the manual menu entries, and include the rules header from the config header.

Handle every new key explicitly in the key dispatch, because an unhandled key falls through to the unknown-key warning and a rules-heavy config would then be a wall of warnings. The keys are: three match keys for class, name and type; a per-rule mode key; and four action keys for no-decorate, position, size and skip-taskbar. Use the hyphenated lower-case naming the rest of the file uses, prefixed `rule-`.

    The group state machine is one sentence a non-programmer can hold: **a new rule begins at the first match-or-mode line that follows an action line, or at the very first rule line in the file.** Consecutive match and mode lines attach to the same rule and are AND-ed/configured; action lines attach to the rule currently open. Keys that are not rule keys are transparent and do not affect the state. Implement it with an explicit `ruleLastWasAction` flag and a small internal dispatcher that receives that flag. `applyFile()` must create/reset the flag at the start of each file, so a system file's final action cannot mutate the first rule from the user file; it must keep appending to the same `rules` vector. Public `applyKeyValue()` should use a member-backed state for deterministic sequential unit-test calls, while the file path uses its per-file state. An orphan or malformed action must warn, leave its action unset, and still set the action-boundary flag so the next match/mode key opens a fresh rule. Document the sentence above as a comment at the top of the block exactly as the menu-entry block documents its own scheme.

Reuse the existing helpers rather than re-deriving them: the boolean parser for the two flag actions, the lower-casing helper before comparing the type and mode vocabularies, and the integer-parse-with-two-catches-and-warn shape for the two coordinate values in the position action and the two dimension values in the size action. Parse position as two comma-separated integers and size as two integers separated by the letter x, matching the forms in the research's worked example; on any parse failure emit the established warning form naming the offending key and leave that action unset.

    An action key arriving with no rule open warns and returns, exactly as a menu-entry follow-on key does with no entry open. An unrecognised type or mode value warns, names the accepted values, and leaves the criterion at its default. A malformed action is still a syntactic action boundary even though it contributes no resolved action.

Deliberately add no CLI flags for rules. Repeated ordered groups do not map onto the command-line option model, and the existing enable/negate flag pairs exist for scalar booleans only. Note that in a comment so the omission reads as a decision.

- **RULES-01 / concurrency** — the probe asks: "If interrupted or run in parallel, what is guaranteed?" Assumption: config parsing is single-threaded, happens once at WM startup before the event loop begins, and reads files the WM never writes.
