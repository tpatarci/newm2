    - Test 3: a position rule that would put a window partly offscreen is clamped so the whole window is visible, and the window is moved rather than shrunk.

  <action>
Add a private method to `Client` that folds the configured rules against this window and applies the resolved outcome, plus two private flags recording whether this window is rule-undecorated and rule-skip-taskbar. Call it in the map path immediately after the class read from Task 1 and before the existing undecorated early-return.

**No-decorate.** When the fold resolves the no-decorate action to true, take the same early-return the dock and notification types already take. Set the rule-undecorated flag first so later code can tell a rule-undecorated window from a dock, then reuse the existing block verbatim rather than writing a parallel one — it already maps the window, sets normal state and updates the client list correctly. Do not trigger the dock-specific workarea recomputation for a rule-undecorated window; it has no struts and is not a dock.

**Position and size.** When the fold resolves either action, apply it to the window's geometry fields at the point in the map path where the client's requested geometry is being negotiated, before the framing and gravity work consumes those values — so the rule participates in the existing negotiation rather than fighting it afterwards. Respect the existing minimum-size floors: a rule asking for a size below the computed minimum is raised to the minimum, exactly as a client request would be. After applying, pass the result through the existing clamp so an out-of-range rule value moves the window fully on screen instead of stranding it; the clamp already moves rather than resizes, which is the right behaviour here too.

**Skip-taskbar.** When the fold resolves it to true, set the flag and let the existing state-publication function emit both the skip-taskbar and skip-pager states — add the two conditional appends inside that function beside the existing ones. Both atoms were interned and advertised in plan 08-08, so compliant panels will honour them. Never write the state property from a second place; the single-publisher invariant is what keeps the state array consistent.

Deliberately implement no workspace action. The WM reports a single desktop by design, so the action from the original requirement wording has nothing to target. Record that at the fold with a comment naming the decision, so a future reader sees an excluded action rather than a forgotten one.

Cite the governing decisions in comments in the codebase's established form: the shipping action set with the workspace exclusion, and the later-wins ordering.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| X client → WM | The class hint is client-supplied, server-allocated, and entirely untrusted |
| Config file → window geometry | Rule position and size values become geometry applied to real windows |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-8-PROP | Tampering | `XGetClassHint` read and the two server-allocated strings | medium | mitigate | Status checked before use, both string fields freed on every path including early returns, and the copied length bounded so a client cannot force an unbounded allocation. Test 2 pins the absent-hint case and the ASan run pins the leak. |
| T-8-STRUT | Denial of Service | Rule-supplied position and size applied to a window | medium | mitigate | Rule geometry is raised to the existing minimum-size floors and then passed through the existing clamp, so an absurd value moves the window fully on screen rather than stranding it. Test 3 pins this. |
| T-8-SHELL | Elevation of Privilege | The applied rule action set | high | mitigate | Only three actions are implemented and none executes anything; the source-level criteria in plan 08-09 and the prohibition here both enforce it. |
| T-8-SPOOF | Spoofing | A hostile client setting a class hint matching another application's rule | low | accept | A client can claim any class, so a rule keyed on class can be triggered by an impostor. The consequence is limited to the three cosmetic actions — no decoration, a position, or a taskbar hint — none of which grants capability. The user's own config defines the rules, and X11 offers no client authentication to key on instead. |
| T-8-SC | Tampering | No package installs in this plan | low | accept | This plan adds no dependency of any ecosystem; nothing to audit. |
</threat_model>
