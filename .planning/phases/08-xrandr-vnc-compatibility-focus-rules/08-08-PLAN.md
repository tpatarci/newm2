<objective>
Implement focus-stealing prevention: compare a newly mapped window's user-time timestamp against the WM's last real user interaction, map stale windows unfocused with an attention hint, and arbitrate activation client messages instead of always granting them — resolving, on the record, a direct conflict with a locked Phase 6 decision.

Purpose: FOCUS-01 is an access-control decision about which client may seize input focus. Implemented only at map time it would be trivially bypassable, because any application can simply send an activation request instead.
Output: five new atoms advertised as supported, a last-user-interaction clock, map-time arbitration, client-message arbitration, a configurable off switch, and tests for each branch.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>How should the WM handle `_NET_ACTIVE_WINDOW` activation requests now that FOCUS-01 requires focus-stealing prevention?</decision>
  <context>
Phase 6 locked decision D-10 chose "always grant" for activation client messages, and the code comment at the handler in `src/Events.cpp` says so explicitly. FOCUS-01 requires focus-stealing prevention. If activation requests keep being granted unconditionally, the feature is bypassable and effectively cosmetic — an application that wants focus simply asks for it instead of relying on the map-time path.

This is a cross-phase decision conflict. The phase's own governing principle is that Phase 8 must not silently narrow: where a requirement cannot be met as written alongside an existing decision, the conflict gets recorded and resolved, not quietly ignored. This checkpoint exists so the reversal of a locked decision from a completed phase is an explicit, recorded choice rather than a side effect of a later commit.

The EWMH specification provides the mechanism: the activation message carries a source indication — 1 for an application, 2 for a pager — and a timestamp, and states the window manager may refuse the request, for example by using the demands-attention state instead.
  </context>
  <options>
    <option id="option-a">
      <name>Arbitrate by source indication (research recommendation, consistent with D-18 and D-19)</name>
      <pros>Honours pager-sourced requests unconditionally, so taskbars and window switchers keep working. Arbitrates application-sourced requests against the message timestamp, which is exactly the attack FOCUS-01 exists to stop. Grants source-less legacy requests, so older clients are not punished, matching D-19's reasoning for the map-time path. Refusal is visible via the demands-attention state rather than silent.</pros>
      <cons>Overturns Phase 6 D-10 and requires amending its record. Slightly more code than a blanket rule. An application that lies about its source indication is still granted — but such a client could equally forge a fresh timestamp, so the ceiling is the same.</cons>
    </option>
    <option id="option-b">
      <name>Keep always-grant; implement FOCUS-01 at map time only</name>
      <pros>Phase 6 D-10 stands unchanged; no cross-phase amendment needed. Smallest diff.</pros>
      <cons>Leaves the feature trivially bypassable, so FOCUS-01 would be claimed but not delivered — precisely the "prove, don't claim" failure this phase exists to prevent.</cons>
    </option>
    <option id="option-c">
      <name>Arbitrate every activation request regardless of source</name>
      <pros>Strongest prevention; one rule with no special cases.</pros>
      <cons>Breaks pagers, taskbars and window switchers, which legitimately activate windows on the user's behalf with a timestamp the WM has no reason to trust as recent. Contradicts the spec's intent for source indication 2.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Selecting option-a or option-c also authorises amending the Phase 6 D-10 record in `.planning/phases/06-ewmh-compliance/06-CONTEXT.md` with a note pointing at this decision.</resume-signal>

    - Test 2: a window mapped with a user-time older than the last user interaction is not focused, the previously active window keeps focus, and the demands-attention state is present on the new window.
    - Test 3: a window mapped with no user-time property at all is focused (legacy client behaviour).
    - Test 4: a window mapped with a user-time of exactly zero is not focused, honouring the spec's explicit request.
    - Test 5: a window that sets the user-time-window property and writes its timestamp on that proxy window is arbitrated using the proxy's value, not the toplevel's absence.
    - Test 6: with the off switch disabled, every one of the above windows is focused — the feature is genuinely switchable.
    - Test 7: once a refused window is subsequently activated by the user, the demands-attention state is cleared.

  <action>
Add the configuration off switch first, since the arbitration consults it. Put a new boolean in the focus block of `include/Config.h`, defaulting to on, with a name matching the existing key style. Handle its key in the boolean section of the config parser, and add the enable and negation CLI flag pair plus their dispatch branches, following the established Phase 5 shape exactly. Extend the config unit tests to assert its default and all four precedence steps. Legacy X clients that set no user-time property would otherwise feel broken, which is why the switch exists.

Then add the arbitration to `Client`. Declare a predicate that answers whether a newly mapped window should receive focus, plus a method that marks a window as demanding attention.

The predicate returns true immediately when the off switch is disabled. Otherwise it determines which window carries the timestamp: read the user-time-window property first and, if it names a valid window, read the timestamp from that proxy rather than from the toplevel — clients use the proxy so they can update the timestamp without generating property events on the toplevel. Then read the user-time property. If it is absent, return true. If it is exactly zero, return false; the spec assigns that value the explicit meaning of asking not to be focused on map. Otherwise compare against the manager's last-user-interaction clock using a signed delta rather than a direct comparison — X timestamps wrap roughly every fifty days, and a bare comparison produces a complete focus outage once per wrap. Grant focus when the window's timestamp is at least as recent.

Both property reads must follow the existing bounded, type-checked, always-freed pattern used by the window-type reader: check the returned type, format and item count before trusting the data, cap the request length, and free the returned buffer on every path. Client-supplied properties are untrusted input.

The refusal path must not be silent. The attention method adds the demands-attention state through the single existing state-publication function — never by writing the state property directly from a second place — and additionally sets the urgency flag in the window's WM hints so a client's own conventions can notice. Clear the state when the window is later activated, since the specification says the WM should unset it once the window got the attention it asked for.

Wire the predicate into the map path so that a refused window is still mapped and still fully managed — it just does not become the active window. Refusal means "mapped in the background with a hint", never "not shown".
  </action>
