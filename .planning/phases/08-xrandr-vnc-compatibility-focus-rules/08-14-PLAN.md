  <action>
Create `scripts/capture-display-capabilities.sh`, taking a display name and a label, and writing everything under a per-label directory beneath the phase's evidence directory. Same shell conventions as the other scripts.

It captures, in one pass: the server's extension list and the specific presence or absence of the Shape, RANDR and RENDER extensions — those three lines are the XDIS-05 matrix; the display geometry, resolution and root depth; the RANDR query output, tolerating and recording the case where the extension is missing rather than aborting; the resolution of the two fontconfig patterns the WM actually requests; the root EWMH properties the checklist names; and the full window tree. Also record the commit hash, the branch, the tool versions, and the timestamp, since the evidence list requires them per signoff.

Write the human-readable summary to a capabilities file and the property and tree dumps to their own files, so a reviewer can diff one target against another.

Then create `tests/test_wm_resource.cpp` tagged `[wm_resource_budget]` implementing the D-32 check as a real pass/fail bar rather than a recorded number. The order matters: measure first, then set the budget from the measurement, and record both.

The case launches the WM through the fixture, measures resident memory with zero, one, five and twenty simple clients mapped, and asserts the twenty-client figure stays under a documented budget. Derive that budget from the measured twenty-client figure with generous headroom, write the derivation and the raw measurements into the test's output and into the evidence directory, and put the resulting number in the test as a named constant with a comment recording the date and host it came from. Do not choose a number before measuring one.

Add a second assertion for idle CPU: with the twenty clients mapped and no input, sample the WM process's accumulated CPU time across a window of at least thirty seconds and assert the increase is under one percent of wall-clock time. This is the same property the checklist's no-steady-CPU-spin item asks for, and it is the observable consequence of the event loop blocking rather than polling — including in the auto-raise-off configuration gated in plan 08-07.

In `CMakeLists.txt`, add a `test_wm_resource` target cloned from `test_wm_runtime`, and give it a per-test timeout generous enough for the thirty-second idle sample.

Mark the capture script executable in git.

Create `docs/RELEASE-NOTES.md` — the project's first release-notes file — covering what Phase 8 changed from a user's point of view. It must state, plainly and findably:

- **The single-screen limitation.** The X screen is treated as one rectangle regardless of how many physical outputs or CRTCs it spans. Windows are clamped to that whole rectangle, not to the nearest output. This is deliberate for the VNC and VPS targets, and per-output awareness is a possible future capability, not an oversight.
- **Focus behaviour changes.** Focus-stealing prevention is on by default and how to turn it off; the three focus-policy settings now actually work and their defaults were corrected to match what the binary already did.
- **Window rules.** The config syntax, the one-sentence rule for where a rule begins, the three shipping actions, and the explicit note that a workspace action is not available because the WM is single-desktop.
- **Degraded-server behaviour.** What happens without the Shape extension, without RANDR, and without XRender — including that tab labels may render unrotated or be absent on a server without XRender, which is a visible difference users should not be surprised by.
- **Remote-desktop support status.** The three tested targets and the one untested one.

Do not copy the X access-control-disabling server flag from any test recipe into these notes. It appears throughout the test fixtures and the checklist's smoke commands and is appropriate there, but a deployment recipe that carries it would disable access control on a user's real session.
