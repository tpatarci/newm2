Create `tests/test_wm_runtime.cpp` tagged `[wm_config_runtime]`, reusing the fixture and input-driver idioms from the preceding test files.

The discipline that makes this group worth writing: every assertion observes the running binary through the X server, never the parser. For colours, capture the relevant window region into an image with a server-side image fetch and compare pixel values between a default run and a configured run — comparing two runs rather than asserting an absolute colour avoids depending on the exact allocation the server returns.   <action>
Extend `tests/test_wm_runtime.cpp` with a group tagged `[wm_stress]` containing a cycle that creates, maps, unmaps and destroys at least one hundred windows against the running binary, then asserts the WM is still correct rather than merely still alive.

Structure the cycle so it exercises interleaving, not just repetition: create a batch, map them all, unmap a subset, destroy a different overlapping subset, map more, and only then tear the rest down. A strictly sequential create-and-destroy loop would miss the container-mutation ordering that a batch with overlapping subsets exercises.

Assert four things after the cycle. First, the client list on root is empty — no stale entries survived. Second, the active-window value names no destroyed window. Third, a freshly mapped window is still framed and managed correctly, proving the WM is functional and not merely running. Fourth, the WM's resident memory has not grown beyond a documented multiple of its post-startup baseline; measure the baseline after the first window is managed, not at process start, so the one-off allocations of initialisation are excluded.

The primary evidence is the sanitizer run: the fixture already collects the child's reports at teardown, so a use-after-free or a leak in the repeated path fails the case automatically. Run the case in the debug tree too, since the sanitizer slows the child roughly twofold and a deadline tuned only for the sanitizer would hide a timing regression in the ordinary build.

Also fold in the checklist's zombie-process robustness item, which shares this case's shape: after the cycle, assert the WM has no zombie children, which exercises the double-fork spawn path's reaping guarantee alongside the window churn.

Poll for each state transition with a deadline. With a hundred windows a fixed sleep would either make the case slow or make it flaky, and under the sanitizer it would be both.
