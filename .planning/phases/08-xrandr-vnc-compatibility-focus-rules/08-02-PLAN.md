  <action>
Create `scripts/gates/build-all.sh` implementing D-04 blockers 1 and 2 as one runnable command. Same shell conventions as `scripts/preflight.sh`.

Behaviour: run `scripts/preflight.sh` first and abort if it fails. Then for each of the three trees in order — `build/debug` (`CMAKE_BUILD_TYPE=Debug`), `build/release` (`CMAKE_BUILD_TYPE=Release`), `build/asan` (`CMAKE_BUILD_TYPE=Debug` plus `-fsanitize=address,undefined -fno-omit-frame-pointer` in both `CMAKE_CXX_FLAGS` and `CMAKE_EXE_LINKER_FLAGS`) — configure with `-DBUILD_TESTS=ON`, build with `--parallel`, and run `ctest --output-on-failure --no-tests=error`. All three must be green; the script exits non-zero naming which tree failed.

The `--no-tests=error` is mandatory per D-33 (08-01 Step F) and is not decoration: without it a tree that configured with `BUILD_TESTS=OFF`, or whose test discovery silently produced nothing, reports a green full-suite run having executed zero tests — which would let this gate certify D-04 blocker 2 against an empty set. This script runs the *unfiltered* suite, so there is no label expression here; the flag alone is the protection.

Export the sanitizer environment for the `build/asan` ctest run so that findings inside forked WM children are captured rather than lost: `ASAN_OPTIONS` with `log_path` pointing under the asan tree (never a bare fixed `/tmp` name), a distinctive `exitcode`, `detect_leaks=1` and `abort_on_error=0`; `LSAN_OPTIONS` with `suppressions=` pointing at `tests/lsan.supp` and `fast_unwind_on_malloc=0`; `UBSAN_OPTIONS` with `print_stacktrace=1`. After the asan ctest run, glob the `log_path` prefix and fail the gate if any report file exists, printing its contents.

Capture compiler and linker warnings per tree into `build/<tree>/build.log` and print a summary count, so the checklist's "no new warnings" line has an artifact to point at. Do not fail on warnings in this plan — only record them.

Finally run the checklist's link audit: `ldd build/release/wm2-born-again`, and fail if the output names any library outside the intended runtime set (libX11, libXext, libXft, libfontconfig, libXrender, libXrandr, libfreetype, libm, libstdc++, libgcc_s, libc, ld-linux and their transitive X/font dependencies). In particular a hit on libXtst is a failure, since that library is test-only.

Accept an optional single tree name argument (`debug`, `release`, or `asan`) so a developer can run one tree during iteration; with no argument it runs all three.

Mark the script executable in git.

  </read_first>
  <action>
Implement D-03 as two mechanisms, because the two tools genuinely differ: cppcheck supports a hash-anchored suppression baseline, clang-tidy has no baseline concept at all (its only suppressions are per-line NOLINT comments).

**cppcheck half.** Generate `scripts/analysis/cppcheck-suppressions.xml` by running cppcheck over `src` and `include` with `--enable=all --std=c++17 -Iinclude`, and recording the current findings as hash-anchored suppression entries. Hash anchoring is mandatory: a line-anchored list produces a false "new finding" on every unrelated edit. Enable unmatched-suppression reporting in the gate run so a baseline entry whose code has since been fixed surfaces as stale rather than rotting silently. The gate invocation uses `--suppress-xml` pointed at the baseline plus `--error-exitcode=1`. Exclude `upstream-wm2/` (reference-only, never compiled) and the FetchContent `_deps/` tree from the scan paths.

**clang-tidy half.** Create a top-level `.clang-tidy` with an explicit, deliberately small enforced set in `WarningsAsErrors` — start with the check families that catch the bug classes this phase actually cares about: bugprone-use-after-move, bugprone-dangling-handle, bugprone-branch-clone, cppcoreguidelines-init-variables, and clang-analyzer-core. Set `HeaderFilterRegex` so only this project's own `include/` and `src/` headers are analysed and the Catch2 `_deps/` tree is excluded, or the run is dominated by third-party findings. Everything not in the enforced set is reported but not fatal, so the gate can be tightened over time without a codebase-wide cleanup now.

**The gate script.** Create `scripts/analysis/run-static-analysis.sh` running both halves against `build/debug`'s compilation database, printing a per-tool summary, and exiting non-zero if either half reports a new finding. Accept `--regenerate-baseline` which rewrites the cppcheck XML from the current tree and prints a loud reminder that the diff must be reviewed before committing — this keeps D-03 reversible, since the baseline can be tightened or regenerated at any time.

Mark both scripts executable in git. Record in a header comment of the baseline XML the cppcheck version and the date it was generated, since hash stability is version-dependent.

<task type="auto">
  <name>Task 3: Remove spurious sanitizer noise from the WM's forked children</name>
  <files>src/Manager.cpp</files>
  <read_first>
    - src/Manager.cpp (the `spawn()`, `spawnArgv()` and `launchApp()` double-fork region around lines 760-860 — the intermediate child's terminating call and the grandchild's exec-failure path)
    - .planning/phases/08-xrandr-vnc-compatibility-focus-rules/08-RESEARCH.md (Pitfall 4, "Related live hazard in the WM itself"; Assumptions Log entry A5)
    - COMPILED_CODE_BEHAVIOR_CHECKLIST.md (the "Repeated spawn() calls do not leave zombie processes" robustness item this change must not regress)
  </read_first>
  <action>
In the double-fork spawn path, the intermediate child currently terminates with the C++ standard exit function and the grandchild does the same when exec fails. Both run atexit handlers and static destructors inside a forked copy of the process; under AddressSanitizer this additionally triggers a leak check in the child, producing reports that have nothing to do with a real defect.

Replace those two terminating calls in the forked children with the POSIX immediate-termination call `_exit()` (from `<unistd.h>`), preserving the existing status codes exactly: 0 for the intermediate child's normal path, 1 for the grandchild's exec-failure path. Apply the same treatment to every forked child in `spawnArgv()` and `launchApp()` if they carry their own copies of the pattern. Do not touch the parent-side termination in `WindowManager::fatal()`; that runs in the real process and must keep running destructors.

Add a short comment at each changed site in the codebase's established form explaining that the child must not run atexit handlers or static destructors of a forked copy.

Verify the zombie-reaping behaviour is unchanged: the double-fork exists precisely so the grandchild is reparented to init and never becomes a zombie. Nothing about the fork structure changes here — only how the intermediate child terminates.
  </action>
