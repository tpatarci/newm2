<objective>
Wire RANDR into the WM for the first time — capability query, event selection, event dispatch, the mandatory Xlib cache refresh, and the D-25 reflow — plus the no-RANDR fallback path that has, until now, had no event to hook.

Purpose: there is currently zero RANDR code in the tree. On VNC and XRDP the client resizes the desktop at will, so a WM that never notices is unusable there. Both the RANDR path and the extension-less path must converge on one idempotent handler.
Output: `libxrandr` as a build dependency, `hasRandrExtension()`, `handleScreenGeometryChange()`, the root `ConfigureNotify` branch, the `WM2_FORCE_NO_RANDR` lever, and resolution-change tests on both a RANDR-capable and a RANDR-less server.
</objective>

    - Test 1: shrinking the X screen from 1280x1024 to 1024x768 makes `_NET_WORKAREA` on root read `0, 0, 1024, 768`.
    - Test 2: a window that sat fully within 1280x1024 but lies partly beyond 1024x768 is moved so its whole extent fits, with its width and height unchanged.
    - Test 3: a window that fits within 1024x768 both before and after the resize is not moved at all.
    - Test 4: replaying the resize when the geometry is already 1024x768 changes nothing — no window moves, `_NET_WORKAREA` is unchanged.
    - Test 5: a fullscreen client is not repositioned by the reflow.
  </behavior>
  <action>
Add `void handleScreenGeometryChange();` to the private section of `include/Manager.h` beside the other event-handling members, and define it in `src/Manager.cpp`.

The handler must not trust any event's dimension fields. Multiple events arrive per logical resize and the intermediate ones can carry the pre-resize size — this was observed directly against a live server. Instead: re-read the 08-04 accessors, compare against the last-known width and height members, and return immediately if they are unchanged. That single guard is what makes the handler idempotent across the duplicate delivery and the stale intermediate. When they have changed, store the new values, iterate every managed client calling the existing clamp primitive on each, then recompute the workarea property.

Iterate both the visible and the hidden client vectors, so a client unhidden after the resize is not stranded offscreen.

Then wire the two entry points in `src/Events.cpp`:

- **RANDR path.** In the `default:` arm, before the existing Shape-event comparison, add a branch guarded on the RANDR sentinel being non-negative and the event type equalling the RANDR event base plus the screen-change-notify offset. Its first statement must be the Xlib configuration-update call, passing the event — this is mandatory and non-optional, because Xlib's cached screen dimensions are otherwise never refreshed and every accessor would keep returning the pre-resize geometry forever. Then call the handler.
- **No-RANDR path.** Split `ConfigureNotify` out of the no-op case group into its own case, and branch on the event's window being the root window. On a match, make the same Xlib configuration-update call (it accepts root configure events too) and call the same handler. On a non-match, break exactly as before so nothing else changes.

Both paths converge on one handler, which is why the coalescing guard matters: on a RANDR-capable server both branches fire for the same logical resize and only the first does any work.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| X server → WM | Screen-configuration events and the resulting geometry are entirely server-controlled |
| X client → WM | A client can drive a desktop resize on VNC-style servers, indirectly triggering the reflow of every managed window |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-8-GEO | Denial of Service | `handleScreenGeometryChange()` reflow across all clients | high | mitigate | The coalescing guard means a burst of screen-change events produces at most one reflow pass per distinct geometry, so a client repeatedly resizing the desktop cannot drive unbounded work. |
| T-8-STRUT | Denial of Service | `updateWorkarea()` recomputation after a shrink | medium | mitigate | Existing strut clamping to the screen rectangle is preserved and now runs against the refreshed geometry rather than a stale cache, so an oversized strut cannot outlive a shrink. |
| T-8-RANDR | Denial of Service | Missing RANDR extension on a degraded remote server | high | mitigate | Runtime capability check with a below-zero sentinel and a warn-and-continue path; the root-configure fallback keeps the reflow working with the extension entirely absent. Proven against a real RANDR-less server in Task 3. |
| T-8-SC | Tampering | `libxrandr-dev` build dependency | low | accept | Not an npm/PyPI/crates ecosystem. Long-standing Ubuntu 22.04 archive package from the X.Org upstream, already installed on this host at 1.5.2, verdict OK in the RESEARCH Package Legitimacy Audit with no `[ASSUMED]`/`[SUS]`/`[SLOP]` entries. |
</threat_model>
