<objective>
Implement the heuristic (per D-01/D-02: no runtime LLM/network call) binary classifier for `/usr/bin`: an in-process ELF `.dynamic`-section `DT_NEEDED` reader using the standard `<elf.h>` types (no `libelf-dev` dependency, no subprocess spawning), a GUI-vs-CLI classifier based on known toolkit library substrings, and the `/usr/bin` directory walk that synthesizes `AppEntry::Source::BinaryScan` records for GUI binaries lacking a `.desktop` file.

Purpose: RESEARCH.md measured shelling out to `readelf`/`ldd` per file at 11.4s wall-clock for ~2400 files (process-spawn overhead) -- unacceptable for a fast-startup VPS WM. This plan is the second of three independent backend subsystems in this phase; it is X11-free and unit-testable without Xvfb, following the same architectural separation as `Config`/`DesktopEntry`.

Output: `include/BinaryScanner.h`, `src/BinaryScanner.cpp`, `tests/test_binaryscanner.cpp`, and a `test_binaryscanner` CMake target.
</objective>

RESEARCH.md Pattern 3 / Code Examples (structural reference for the ELF reader -- this project has `<elf.h>` available via glibc, confirmed present at `/usr/include/elf.h`; `libelf-dev` is confirmed NOT installed, so do not `#include <libelf.h>` or link `libelf`):
- `Elf64_Ehdr` fields needed: `e_ident[EI_MAG0..EI_MAG3]` (must equal `ELFMAG0 'E' 'L' 'F'`), `e_ident[EI_CLASS]` (must equal `ELFCLASS64` -- skip+warn on `ELFCLASS32`, this phase only supports 64-bit binaries since /usr/bin on the target Ubuntu 22.04+ VPS is x86_64), `e_phoff`, `e_phnum`, `e_phentsize`.
- Program headers (`Elf64_Phdr`): walk `e_phnum` entries starting at file offset `e_phoff`; find the one with `p_type == PT_DYNAMIC` (gives `.dynamic` section's `p_offset`/`p_filesz` directly, works even on stripped binaries per RESEARCH.md).
- `.dynamic` entries (`Elf64_Dyn`): cast the `PT_DYNAMIC` byte range to `Elf64_Dyn[]`; iterate until `d_tag == DT_NULL`; the entry with `d_tag == DT_STRTAB` gives `d_un.d_ptr`, a *virtual address* that must be translated to a *file offset* by finding the `PT_LOAD` segment whose `[p_vaddr, p_vaddr+p_memsz)` range contains it (file offset = `p_offset + (vaddr - p_vaddr)`); each entry with `d_tag == DT_NEEDED` has `d_un.d_val` as a byte offset *into* that resolved `.dynstr` file region -- read the null-terminated string starting there.
- All of `PT_DYNAMIC`, `PT_LOAD`, `DT_NEEDED`, `DT_NULL`, `DT_STRTAB`, `ELFCLASS64`, `ELFMAG0/1/2/3` are pre-defined macros/constants in `<elf.h>` -- do not hand-redefine them.

GUI-toolkit substring list (RESEARCH.md Code Examples, A3 in Assumptions Log): `libX11`, `libgtk-3`, `libgtk-4`, `libQt5`, `libQt6`, `libwayland-client`, `libSDL2` -- a binary is classified GUI if any `DT_NEEDED` name *contains* one of these substrings.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `/usr/bin` (root-owned system binaries) -> BinaryScanner | Local system binaries are trusted content on a single-user VPS, but the scan must still never execute or `ldd`-trace a candidate file -- only static byte-level parsing is permitted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-7-04 | Tampering (TOCTOU) | `readNeededLibraries()` / `scanUsrBin()` open+read path | low | mitigate | Use `open()` then `fstat()` on the resulting fd (never `stat()` the path then a separate `open()`) for both the executable-bit check and the ELF read, closing the race between permission check and content read; low real-world severity for a local root-owned directory scan but cheap to implement correctly |
| T-7-05 | Tampering / Information Disclosure | ELF parsing of untrusted-shaped (malformed/truncated) binaries | medium | mitigate | Every ELF field access is bounds-checked against `st.st_size` before dereferencing; malformed ELF (bad magic, truncated headers, out-of-range offsets) returns `std::nullopt` and is skipped with a warning, never crashes the scan or the whole WM startup |
| T-7-06 | Information Disclosure | Executing `ldd`/loading the candidate binary to inspect it | n/a (avoided by design) | mitigate | This module never loads or executes scanned binaries -- `ldd` is documented as capable of running target code in some configurations; this implementation only performs static byte-level section parsing via `mmap(PROT_READ, ...)` |
</threat_model>
